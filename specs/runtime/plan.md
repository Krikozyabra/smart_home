# План реализации runtime

Статус: реализация и автоматические проверки завершены на рабочей машине;
аппаратные проверки и ThreadSanitizer не выполнены.
Основание: [spec.md](spec.md), [design.md](design.md), `AGENTS.md`,
staged diff, существующий main.cpp, контракты и тесты затронутых компонентов.

## 1. Соответствие требованиям

| Требование | Реализация | Проверка |
|---|---|---|
| RT-001: обслуживание событий при вводе и фоновой работе | Неблокирующий ввод, poll, события worker | Неполная строка, управляемо задержанный worker, обработка других событий и сигналов |
| RT-002: логика в main.cpp | Композиция и локальные средства приложения | Область diff, отсутствие новой библиотеки runtime |
| RT-003: подготовка и восстановление графа | Базовые комнаты и возможности до цикла, связи при обнаружении | Первый запуск, повторный scan, восстановление связей |
| RT-004: реестры до цикла | DriverFactoryRegistry с фабриками и DeviceRegistry | Создание через фабрики, прежние ID после перезапуска |
| RT-005: службы до цикла | Явные зависимости manager, dispatcher и discovery | Запуск, ошибки открытия ресурсов, освобождение |
| RT-006: обнаружение и команды | Две лампы и датчик, адресные и групповые команды | Все операции, неверные аргументы, отсутствие целей, частичный успех |
| RT-007: сохранение после изменений | RAM-снимки, worker, поколения и CURRENT | Каждая изменяющая операция, отказ и повтор, прерывание фиксации |
| RT-008: восстановление и RAM | Загрузка одного поколения, рабочие базы в RAM | Инвентарь и значения, повреждение снимка, отсутствие disk fallback |
| Штатное завершение | exit, EOF, SIGINT/SIGTERM, финальная фиксация и join | Повторный запуск после каждого варианта, ошибка финального сохранения |
| Ограничение ресурсов | Ограниченная очередь и эксклюзивный flock | Отклонение изменения до выполнения при заполнении, второй процесс |

## 4. Автоматические проверки

Основные тесты воспроизводимы без сети, MQTT broker, микрофона и моделей ИИ.
Каждый получает изолированные постоянный и RAM-каталоги. Тесты общаются
с процессом через stdin/stdout и наблюдают результаты сохранения.
Для отказов в точках протокола и задержанного worker допустимы приватные
точки доступа только в тестовой сборке main.cpp, без публичных команд
управления тестовыми ошибками в рабочей сборке и без нового модуля.

| Сценарий | Существенные проверки |
|---|---|
| Первый запуск | Службы до цикла, три устройства, базовые комнаты и возможности связаны с инвентарём |
| Повторный scan | Не меняются ID, количество, имена, включение, яркость, цвет и температура; нет дубликатов связей |
| Адресные команды | Чтение и изменение всех поддерживаемых возможностей; типы, значения, отсутствие изменения после ошибки |
| Групповые команды | Две лампы комнаты изменены, отдельные результаты, нет совпадений, неизвестный тип/комната, частичный успех |
| Разбор ввода | Пустая строка, лишние/недостающие аргументы, отрицательный/переполненный ID, неизвестная операция, boolean, яркость, RGB до сужения типа |
| События | Неполная строка не блокирует события; worker не блокирует чтение и команды; сигналы обрабатываются при потоке ввода |
| Сохранение после изменения | Каждая логическая изменяющая операция, включая частичный успех группы, получает снимок; чтение и прежнее значение не создают лишний |
| Восстановление | После подтверждения и перезапуска совпадают инвентарь, ID, все значения, комнаты и связи |
| Ревизии | Старое подтверждение не помечает новые изменения сохранёнными; комплект принадлежит одной ревизии |
| Ошибка подготовки/записи | Изменения остаются в RAM, действие и сохранение различаются, прежняя фиксация доступна, save повторяется успешно |
| Прерывание фиксации | До/после записи файлов, публикации поколения, rename CURRENT и fsync каталога; после запуска выбирается целый комплект |
| Повреждение | Неверная версия, повреждённый CURRENT, отсутствующий файл, несогласованные метаданные: ошибка запуска без сброса |
| Очередь | Заполнена — изменение отклоняется до выполнения; чтение и завершение доступны; финальный снимок ждёт места |
| Завершение | exit, EOF, SIGINT/SIGTERM, непустая очередь, успешная финальная фиксация, ненулевой выход и сохранённые файлы при отказе |
| Владение | Второй процесс отклонён; частичные ресурсы освобождаются; worker не обращается к уничтоженным объектам |
| RAM и конфигурация | Нет скрытого fallback; недоступность RAM и конфликт параметров дают диагностируемую ошибку |
| Logging CLI | Ошибки конфигурации до бизнес-работы, диагностика в stderr, off подавляет обычные логи, интерактивный запуск успешен |

Конкурентные проверки синхронизируются подтверждениями, событиями,
condition_variable или управляемыми точками остановки. Произвольный sleep
не доказывает нужный порядок. Процессные CTest-проверки имеют тайм-аут.
Восстановление после аварии проверяется отдельным процессом, а не только
повторным открытием объекта.

Существующие проверки атомарного файла ontology не заменяют проверку
общего протокола: сами по себе они не доказывают согласованность SQLite и графа.

## 5. Команды проверки реализации

Использовать отдельный build-каталог. Параметры установленных Ladybug SDK
и ONNX Runtime передавать согласно реальной конфигурации среды.
Runtime не запускает audio/OWW/MQTT, однако корневой CMake пока собирает
эти модули и сохраняет их существующие зависимости.

```sh
cmake -S . -B /tmp/smart-home-runtime/build -DCMAKE_BUILD_TYPE=Debug
cmake --build /tmp/smart-home-runtime/build -j 4
ctest --test-dir /tmp/smart-home-runtime/build --output-on-failure
cmake --build /tmp/smart-home-runtime/build --target docs
git diff --check
```

После добавления тестов выполнить отдельный набор:

```sh
ctest --test-dir /tmp/smart-home-runtime/build -R '^runtime_' --output-on-failure
```

Проверить форматирование изменённого C++ принятой версией clang-format.
При наличии поддержки выполнить ThreadSanitizer для очереди, worker
и завершения. Невозможность запуска отметить отдельно от результата тестов.

## 9. Результаты реализации (2026-11-09)

Реализованы RT-001…008 в src/main.cpp, необходимые CMake-зависимости,
процессные RuntimeTests.py и адаптация LoggingCliTests.cmake.
README приведён в соответствие с новым запуском и конфликтом старых
ontology-параметров. Публичные контракты модулей не изменены.

Четыре CTest-набора runtime содержат 13 процессных сценариев с отдельными
подслучаями. Проверяются команды и повторный scan, восстановление всех
значений и связей, частичный успех группы, EOF без newline, длинная строка,
сигналы, очередь, single-writer, старое подтверждение при новой ревизии,
отказы подготовки/фиксации и повтор save, финальный отказ после ранее
сохранённой той же ревизии, повреждение поколения, конфигурация и RAM.
SIGKILL выполняется на восьми этапах публикации; после каждого проверяется
целый комплект и восстановление отдельным процессом. Порядок конкурентных
проверок задают FIFO и inotify, а не произвольные задержки.

ThreadSanitizer пытались включить отдельной конфигурацией:

```sh
cmake -S . -B /tmp/smart-home-runtime/tsan -DCMAKE_BUILD_TYPE=Debug \
  -DSMART_HOME_LADYBUG_SDK_DIR=/home/prince/Projects/lbdb_test -DBUILD_DOCS=OFF \
```

`BufferManagerException: Mmap for size 8796093022208 failed`.
Проверка SDK не обходилась; TSAN-тесты не запущены, отсутствие гонок
по результатам TSAN не заявляется.

Не выполнены: измерения задержек/CPU/RAM на Raspberry Pi, запись и fsync
на целевой SD-карте, длительный прогон и физическое отключение питания.
SIGKILL проверяет границы публикации процесса, но не заменяет проверку
сбоев питания накопителя. Микрофон, обученные модели и иные аппаратные
проверки вне границ runtime не выполнялись.
