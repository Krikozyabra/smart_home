# Технические решения runtime

Статус: реализовано в src/main.cpp; результаты проверок — в plan.md.
Основание: [spec.md](spec.md), [plan.md](plan.md), `AGENTS.md`, staged diff,
существующие реализации и тесты затронутых компонентов.
Целевая платформа — Linux, Raspberry Pi 4b 8/120 (SD-card), приложение C++17.

## 1. Границы и согласованные решения

Runtime собирает приложение в `src/main.cpp`. Отдельная библиотека
и публичный интерфейс runtime не создаются. Вспомогательные типы и функции
находятся в анонимном пространстве имён этого файла.

Текущий сценарий объединяет обнаружение, инвентарь, фабрики и реестры,
управление устройствами через консоль, онтологию и logging.
MQTT, audio, OWW и обработка текста не подключаются.

RT-001 означает обслуживание событий при ожидании ввода и фоновой работе.
Постоянная загрузка ядра на 100% и CPU affinity не нужны.
Численного предела задержки и гарантии hard real-time нет. Будущие длительные
вычисления выполняются отдельно, возвращая результаты событиями;
универсальный пул ИИ-задач на этом этапе не создаётся.

Рабочий инвентарь, значения устройств, граф и промежуточные снимки находятся
в RAM. После каждой изменившей состояние логической операции запрашивается
сохранение полного состояния. Периодического сохранения нет.

## 2. Устранённые расхождения с исходной реализацией

| Исходное поведение | Реализованное изменение |
|---|---|
| main.cpp создаёт драйверы напрямую и выполняет разовую демонстрацию | Цикл и создание через discovery, DeviceManager и фабрики |
| DeviceRecord содержит только инвентарные поля | Отдельная таблица runtime для значений возможностей; контракт DeviceRecord сохраняется |
| Фабрика лампы задаёт начальные значения | После создания сохранённого драйвера восстанавливаются включение, яркость и цвет |
| Готовой фабрики датчика температуры нет | Локальная фабрика приложения, реализующая IDeviceDriverFactory |
| SQLite и ontology сохраняются независимо | Публикация согласованного поколения runtime |
| В ontology по умолчанию работает 30-секундный worker | Runtime использует sync_interval = 0 и управляет фиксацией сам |
| LoggingCliTests.cmake ожидает разовый демонстрационный вывод | Тест передаёт команды интерактивному приложению, сохраняя проверки logging |

Принятые уточнения отражены в [spec.md](spec.md). Поведение ontology
как самостоятельной библиотеки не меняется. Посторонних рефакторингов нет.

## 3. Конфигурация, зависимости и владение

Локальная конфигурация runtime отделяет проверку параметров от открытия
ресурсов. Базовые настройки:

| Настройка | По умолчанию | Проверка |
|---|---|---|
| Каталог постоянного состояния | data/runtime | Непустой путь; проверка доступа при открытии ресурсов |
| Базовый каталог RAM | /dev/shm | Приватный рабочий каталог на RAM-файловой системе; fallback выключен |
| Ёмкость очереди снимков | 4 комплекта | Положительное число; учитывает выполняемый, ожидающие и зарезервированные комплекты |
| Периодическая синхронизация ontology | 0 секунд | Отключена на уровне композиции runtime |
| Disk fallback ontology | false | Не может обходить требование работы в RAM |

Ёмкость 4 — исходный параметр реализации, а не доказанный лимит расхода RAM
на плате. Проверки места в tmpfs и отказа выделения ресурсов остаются нужны.

Logging использует существующий механизм разрешения конфигурации.
Настройки main и ontology согласуются с единым каталогом состояния:
автономный постоянный файл не должен обходить публикацию поколения.
Конфликтующие параметры отклоняются явно, без молчаливого игнорирования.

| Компонент | Владение и зависимости |
|---|---|
| Logging session | Живёт до завершения диагностики приложения |
| Lockfile состояния | Эксклюзивный flock на запуск, восстановление, сохранение и очистку |
| RAM-каталог и рабочие базы | RAII-владелец; закрытые каталоги, без disk fallback |
| SQLiteDeviceStorage | Рабочая SQLite-база в RAM, источник инвентаря |
| Сохранённые значения возможностей | Собственные значения, доступные при восстановлении драйверов |
| DriverFactoryRegistry | Владеет фабриками через unique_ptr |
| DeviceRegistry | Владеет активными драйверами через unique_ptr |
| DeviceManager | Ссылается на storage и оба реестра |
| LadybugOntologyStorage | Владеет RAM-графом и внутренними ресурсами SDK |
| CommandDispatcher | Ссылается на реестр устройств |
| DiscoveryService | Ссылается на manager, владеет источником обнаружения |
| Worker сохранения | Владеет потоком и принятыми снимками, не обращается к живым драйверам |

Все сервисы получают зависимости явно. Основной поток — единственный
владелец изменения активных устройств. Ссылки не передают владение.
Деструкторы не выпускают исключений; ошибки финального сохранения
и `ontology.close()` проверяются явно.

## 4. Запуск и восстановление

1. Разобрать и проверить конфигурацию; создать logging session.
2. Получить эксклюзивную блокировку состояния. Lockfile не удалять:
   его inode сохраняет смысл блокировки при замене снимков.
3. Прочитать CURRENT, проверить формат и комплектность выбранного поколения.
   Первый запуск без зафиксированного состояния допускается. Повреждённый
   указатель или отсутствующий файл зафиксированного поколения — ошибка,
   а не повод начать с пустого состояния.
4. Создать приватный RAM-каталог. Скопировать в него зафиксированные SQLite
   и ontology либо подготовить новые рабочие базы.
5. Открыть SQLite через существующий SQLiteDeviceStorage. Проверить таблицу
   значений runtime, поддерживаемые типы, диапазоны и согласованность ID.
6. Создать оба реестра, зарегистрировать фабрики и создать DeviceManager.
   Вызвать restoreStoredDevices() и восстановить значения возможностей.
7. Открыть ontology; проверить связи с инвентарём. Подготовить недостающие
   базовые комнаты и возможности, сохраняя существующие данные.
   Инициализационные изменения также требуют фиксации.
8. Создать dispatcher, simulated discovery source, discovery service,
   каналы событий и worker сохранения. Затем войти в цикл.

Сохранённая лампа создаётся существующей фабрикой, после чего её значения
восстанавливаются через операции dispatcher. У датчика интерфейс
ITemperature допускает только чтение: локальная фабрика получает сохранённую
температуру при создании драйвера. Данные, на которые ссылается фабрика,
живут дольше неё. Для нового датчика используется 23 °C.

Порядок строк SQLite не используется для назначения ID. Сохраняется сама
база с прежними ключами и счётчиком SQLite. Отсутствующие или некорректные
значения устройства в зафиксированном снимке не заменяются начальными.

## 5. Обнаружение и онтология

На первой итерации вызывается `DiscoveryService::scanOnce()` с источником:

| Физический ID | Driver ID | Тип онтологии | Комната | Начальное состояние |
|---|---|---|---|---|
| SIM-LIGHT-001 | simulated.light | light | living_room | Выключена, 50%, RGB 255/255/255 |
| SIM-LIGHT-002 | simulated.light | light | living_room | Выключена, 50%, RGB 255/255/255 |
| SIM-TEMP-001 | simulated.temperature_sensor | temperature_sensor | bathroom | 23 °C |

Операция доступна и по `scan`. Регистрация проходит через manager,
storage и фабрики. Повторное обнаружение сохраняет инвентарь, имена, ID
и текущие значения. Обработчики консоли не создают драйверы напрямую.

Комнаты имеют ID `living_room` и `bathroom`, названия «Гостиная»
и «Ванная комната». Возможности используют CapabilityDescriptor::getId():
`on_off`, `brightness`, `color`, `temperature`.
Записи и связи добавляются идемпотентно; существующее назначение комнаты
не перезаписывается каждым повторным scan.

Runtime дополняет недостающие записи и связи графа по ID, назначенным storage.
Физические адреса остаются в инвентаре. Пользовательских команд
редактирования графа пока нет.

DiscoveryReport обрабатывается с учётом уже залогированных ошибок.
При частичном сбое регистрации или дополнения графа приложение
не утверждает, что обнаружение целиком успешно. Успешные изменения остаются
в RAM; повторный scan должен завершать недостающие шаги.
Несогласованный комплект не публикуется как полное поколение.

## 6. Цикл событий и консоль

Цикл обслуживает готовность stdin, запрос завершения и результаты worker.
Poll и неблокирующее чтение накапливают строку без блокирующего getline
после получения лишь части ввода. Если меняются настройки терминала
или флаги дескрипторов, они восстанавливаются через RAII.
При EOF обрабатывается накопленная последняя непустая строка, даже без
завершающего newline, затем начинается штатное завершение.

Одна итерация выполняет конечный объём работы; поток строк не вытесняет
обработку сигналов и результатов сохранения. Активного ожидания нет.
Подготовка снимка в RAM и текущие операции устройств выполняются между
событиями: абсолютной нулевой задержки это не гарантирует.
Их стоимость требуется измерить на Raspberry Pi.

| Команда | Поведение |
|---|---|
| help | Синтаксис, типы и доступные операции |
| list | Локальный ID, имя, тип и комната каждого устройства |
| `show <id>` | Описание, возможности, значения и связи одного устройства |
| scan | Повторное обнаружение и дополнение графа |
| save | Запрос сохранения текущего состояния, включая ранее не сохранённое |
| exit | Штатное завершение |
| `<id> <operation> [arguments]` | Адресное выполнение через dispatcher |
| `<room> <type> <operation> [arguments]` | Выполнение для всех совпавших устройств |

Парсер проверяет целочисленный неотрицательный DeviceId, число аргументов,
полное преобразование чисел и переполнение. Boolean записывается как
`true` или `false`. RGB — три целых 0…255; проверка предшествует
преобразованию в компоненты цвета. Яркость передаётся как int, диапазон
0…100 проверяет dispatcher. Неизвестная операция или несовместимые аргументы
дают ошибку команды; дополнительная доменная диспетчеризация не создаётся.

Групповой выбор использует ID комнаты и тип записи онтологии.
Список целей фиксируется до выполнения и сортируется по DeviceId.
Каждая цель проходит через dispatcher. Нет совпадений — ошибка без изменения
состояния. Для каждой цели выводится результат или ошибка.
Успешные действия не откатываются при ошибке другой цели.

Для сохранения одна адресная команда, одна групповая команда или один scan —
одна логическая операция. Если состояние изменилось, включая частичный успех,
формируется новая ревизия. Чтение, повторная установка прежнего значения
и scan без изменений нового снимка не требуют.

## 7. Полное состояние и подготовка снимка

Рабочая SQLite-база содержит существующую таблицу devices, отдельную таблицу
значений возможностей runtime и сведения о версии/ревизии.
Значения привязаны к локальному ID и типу устройства. DeviceRecord
и публичный IDeviceStorage не расширяются состоянием ламп.

Дополнительные SQLite-ресурсы runtime имеют RAII-владельцев.
Пользовательские значения передаются параметрами, а не собираются в SQL.
Обращения к рабочей базе принадлежат основному потоку; worker живую базу
не открывает.

На границе событий основной поток:

1. Считывает фактические значения через интерфейсы возможностей
   и транзакционно обновляет их таблицу в рабочей SQLite-базе.
2. Создаёт самостоятельную RAM-копию SQLite через backup API.
   Простое копирование открытого файла и его журналов не используется.
3. Вызывает ontology.sync(). Работает штатный протокол ontology:
   checkpoint, закрытие движка, временный файл, fsync, rename,
   fsync каталога и повторное открытие. Целевой файл этого этапа в runtime
   находится в RAM и является промежуточным checkpoint.
4. Подготавливает неизменяемую RAM-копию checkpoint ontology и метаданные
   той же ревизии. Последующие события не меняют эти копии.
5. Передаёт комплект worker с явной передачей владения временными файлами.

Native sync_interval ontology равен нулю, allow_disk_fallback выключен.
Протокол библиотеки не заменяется прямой записью её базы.
Долговечность полного состояния обеспечивает следующий этап runtime.

## 8. Фиксация поколения

```text
data/runtime/
  runtime.lock
  CURRENT
  generations/
    <generation>/
      state.sqlite
      ontology.lbdb
      metadata
```

Metadata содержит версию формата, ревизию и SHA-256 обоих файлов для проверки
комплектности и согласованности поколения. Runtime приватно использует OpenSSL
Crypto для хеширования; типы SDK в публичный API не добавлены. CURRENT выбирает законченное поколение
внутри каталога состояния; произвольный путь наружу не принимается.

Единственный worker последовательно выполняет:

1. Создание временного каталога поколения на той же файловой системе,
   где находятся постоянные поколения.
2. Запись state.sqlite, ontology.lbdb, metadata, проверку ошибок
   и fsync файлов и каталога.
3. Rename каталога в окончательное имя и fsync родительского generations.
4. Запись временного CURRENT, fsync, атомарную замену основного CURRENT
   и fsync каталога состояния.
5. Событие основному циклу с результатом и номером ревизии.

Общей транзакции SQLite/LadybugDB нет: атомарная замена указателя выбирает
весь комплект. Незаконченные или не указанные в CURRENT поколения
не становятся источником восстановления только из-за большего номера.
Предыдущее зафиксированное поколение сохраняется до успешной публикации
нового. Очистка не затрагивает текущее или занятое worker поколение.

При ошибке после rename CURRENT, но до успешного fsync каталога
долговечность замены неопределённа: успех не подтверждается.
После аварии допустим старый либо новый целый комплект, но не смесь файлов.

До начала изменяющей операции резервируется место в ограниченной очереди.
При отсутствии места команда отклоняется до изменения устройств.
Чтение, результаты worker и запрос завершения продолжают обрабатываться.
Успешно принятые изменения не объединяются по таймеру вместо сохранения
после каждой логической операции.

Worker перехватывает исключения и передаёт результат основному потоку.
Подтверждение старой ревизии не означает сохранения более нового состояния.
Ошибка сохраняет признак неподтверждённого состояния. Следующий save,
изменение или завершение запрашивает актуальный полный снимок.

## 9. Диагностика и завершение

Результат изменения отделён от фиксации: «выполнено, сохранение ожидается»,
«ревизия сохранена» или «изменение применено, сохранение не удалось».
Save не блокирует цикл ожиданием worker; результат приходит событием.
Сбой подготовки RAM-снимка тоже оставляет фактические изменения в RAM
с явным статусом несохранённого состояния.

Ошибки команд обрабатываются на их границе. Важность logging определяется
контекстом, не классом исключения. Обработанные ошибки DiscoveryReport
повторно не журналируются. Физические адреса и произвольная полезная
нагрузка по умолчанию в логи не попадают.

SIGINT/SIGTERM только сигнализируют циклу безопасным для обработчика
способом. При exit, EOF или сигнале приложение:

1. Прекращает принимать новые команды и изменения.
2. Дожидается места для финального актуального снимка, продолжая
   обрабатывать результаты worker. Заполнение очереди не отменяет
   попытку финального сохранения.
3. Дожидается финальной фиксации, останавливает и присоединяет worker
   без удержания нужного ему mutex.
4. Явно закрывает ontology и SQLite-ресурсы.
5. Удаляет рабочие каталоги только при безопасном завершении.
   При ошибке финального сохранения сохраняет доступные RAM-файлы
   и сообщает об этом, не удаляя их родительский каталог.
6. Освобождает блокировку состояния после завершения очистки.

Успешный выход — код 0; ошибка конфигурации — код 2, как в существующем main;
сбой запуска/выполнения/финального сохранения — ненулевой код.
SIGKILL и отключение питания не допускают финального сохранения:
восстанавливается зафиксированное поколение, неподтверждённые изменения
могут быть потеряны.

## 10. Интеграция и проверка

`src/CMakeLists.txt` получает необходимые PRIVATE-зависимости приложения,
включая SmartHome::DeviceManagement, SmartHome::Discovery и Threads::Threads.
Приложение остаётся на C++17; стандарт SDK ontology на него не переносится.
Изменяются только необходимые настройки, тесты и вход specs/runtime
в cmake/Docs.cmake.

Основные тесты проверяют наблюдаемое поведение: команды, вывод,
зафиксированные поколения и повторный запуск. Управляемые задержки
и ошибки worker доступны только тестовой сборке, без публичных тестовых
команд в рабочем приложении и без нового модуля.

Сценарии, команды сборки и отдельные проверки на Raspberry Pi приведены
в [plan.md](plan.md). Тесты на рабочей машине не подтверждают задержку,
расход RAM и скорость fsync на целевой SD-карте.

## 11. Детали реализации

Имена CLI и окружения зафиксированы в spec.md. Самостоятельные настройки
ontology отклоняются целиком; runtime не читает их и не принимает отдельный
постоянный путь в обход CURRENT. Рабочая файловая система проверяется через
statfs (tmpfs/ramfs). При первом создании постоянных каталогов fsync
выполняется также для родителей, публикующих новые записи каталогов.

Обработчики сигналов устанавливаются до создания потоков компонентов;
используются lock-free atomic-флаг и неблокирующий self-pipe. Время жизни
обработчиков охватывает завершение всех служб и worker. stdin имеет
O_NONBLOCK на время цикла, прежние флаги восстанавливаются RAII.

Место очереди учитывает резервирование, подготовленный/выполняемый снимок
и результат, ещё не обработанный основным потоком. Результаты worker имеют
предварительно выделенный буфер. Неиспользованный резерв освобождается
при чтении, ошибке и установке прежнего значения. Неудачные промежуточные
копии удаляются; рабочие SQLite и checkpoint сохраняются при ошибке финала.
После успешной публикации worker удаляет остальные поколения. Ошибка
этой необязательной очистки не отменяет подтверждённую фиксацию.

Основная реализация и процессный тестовый исполняемый файл компилируются
из одного main.cpp. Управляемые точки ошибок/пауз включены только для
runtime_test_app через SMART_HOME_RUNTIME_TESTING. Готовый smart_home
не читает переменную окружения управления тестовыми отказами.
