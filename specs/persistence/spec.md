# Персистентность полного состояния и управление поколениями

ID: Persistence

Статус: реализовано в `SmartHome::Persistence`. [Технические решения](design.md) и [план проверок](plan.md).

## Цель

Обеспечить согласованное, атомарное и долговечное сохранение цифровых двойников устройств, инвентаря и семантического графа онтологии на постоянном носителе (SD-карта Raspberry Pi 4b), защищая данные от частичной записи при сбоях питания и исключая блокировку основного потока приложения при медленном дисковом вводе-выводе.

## Требования

- PS-001: Полное согласованное состояние системы сохраняется в виде изолированных нумерованных поколений внутри каталога `<state_dir>/generations/<generation_name>`. Комплект поколения включает:
  1. `state.sqlite` — SQLite-база инвентаря устройств и значений их параметров.
  2. `ontology.lbdb` — файл снимка семантического графа комнат и связей LadybugDB.
  3. `metadata` — текстовый манифест целостности поколения.
- PS-002: Манифест `metadata` содержит сигнатуру `SMART_HOME_RUNTIME 1`, номер ревизии (`Revision`) и контрольные суммы SHA-256 файлов `state.sqlite` и `ontology.lbdb`. Ревизия сверяется с именем каталога и `runtime_meta`; любое несовпадение означает повреждение поколения.
- PS-003: Динамические свойства устройств сохраняются в таблице `device_properties` базы `state.sqlite` по ключу `(device_id, property_key)` с типизацией (`bool`, `int`, `double`, `color`, `string`). Полный набор свойств и ревизия в `runtime_meta` обновляются одной транзакцией (`BEGIN IMMEDIATE` / `COMMIT`). `updated_at` хранит время сохранения в секундах Unix. Старые поколения v1 с таблицей `runtime_values` доступны для восстановления и переходят на новую схему при сохранении.
- PS-004: Публикация поколения выполняется воркером `SaveWorker` в фоновом потоке по строгому протоколу:
  1. Запись файлов во временный каталог `.pending-XXXXXX` на той же файловой системе.
  2. Синхронизация данных через `fsync` для каждого файла и каталога.
  3. Атомарное переименование в окончательное имя поколения `gen-<rev>-<id>`.
  4. Синхронизация `fsync` родительского каталога `generations/`.
  5. Запись временного указателя `CURRENT.tmp` и его `fsync`.
  6. Атомарное переименование `CURRENT.tmp` -> `CURRENT`.
  7. Финальный `fsync` корневого каталога состояния `<state_dir>`.
  8. Отправка события завершения фиксации основному циклу через `EventPipe`.
- PS-005: Поколение считается зафиксированным (committed) только после успешного завершения шага 6 (атомарная замена `CURRENT`). Ошибка до этого момента сохраняет прежнее активное поколение неизменным. Ошибка на шаге 7 (`fsync` каталога) трактуется как неопределённая долговечность и требует повторной фиксации.
- PS-006: `SaveWorker` оперирует изолированными RAM-снимками и никогда не обращается к живым объектам `Device`, активным соединениям SQLite или движку LadybugDB в основном потоке.
- PS-007: Очередь фонового сохранения ограничена настроенной ёмкостью (`capacity`, по умолчанию 4). Слот занят от резервирования `Reservation` до освобождения токена или получения результата. При заполнении очереди изменения отклоняются до выполнения.
- PS-008: На этапе запуска `GenerationManager` читает указатель `CURRENT`, находит активное поколение и валидирует SHA-256 контрольные суммы обоих файлов. Отсутствие зафиксированного поколения трактуется как первый чистый запуск. Повреждённое зафиксированное поколение вызывает фатальную ошибку запуска без автоматического отката к дефолтным значениям.
- PS-009: При ошибке подготовки снимка или сбое записи на диск фактические изменения сохраняются в оперативной памяти (RAM) с установкой флага несохранённого состояния. Повторная попытка выполняется по явной команде `save`, при следующем изменении или при штатном завершении.
- PS-010: После успешного `fsync` корневого каталога `SaveWorker` удаляет устаревшие поколения и оставшиеся `.pending-XXXXXX`. Ошибка очистки сохраняет подтверждение фиксации.
- PS-011: Доступ к каталогу состояния защищается межпроцессной эксклюзивной блокировкой `flock` на файл `runtime.lock`. Второй процесс с тем же каталогом состояния немедленно отклоняется.
- PS-012: Приватные точки управляемых сбоев (`Testing.h`) доступны в `runtime_test_app` для сценариев задержки диска и прерывания процесса в `RuntimeTests.py`. Для `smart_home` их можно явно включить флагом CMake `SMART_HOME_RUNTIME_TESTING=1`. По умолчанию обычная сборка исключает тестовые точки.

## Структура данных и SQLite схема

### Таблица `runtime_meta`:
```sql
CREATE TABLE runtime_meta (
    version INTEGER NOT NULL,
    revision INTEGER NOT NULL
);
```

### Таблица `device_properties`:
```sql
CREATE TABLE device_properties (
    device_id INTEGER NOT NULL,
    property_key TEXT NOT NULL,
    value_type TEXT NOT NULL,
    raw_value TEXT NOT NULL,
    updated_at INTEGER NOT NULL,
    PRIMARY KEY (device_id, property_key),
    FOREIGN KEY (device_id) REFERENCES devices(local_id) ON DELETE CASCADE
);
```

### Формат манифеста `metadata`:
```text
SMART_HOME_RUNTIME 1
<revision>
<sha256_state_sqlite>
<sha256_ontology_lbdb>
```

### Формат указателя `CURRENT`:
```text
gen-<revision>-<unique_suffix>\n
```

## Ошибки и инварианты

- Попытка публикации снимка при незарезервированном слоте очереди запрещена (`std::logic_error`).
- Отрицательный номер ревизии или переполнение `int64_t` вызывает `std::runtime_error`. Реактор проверяет следующую ревизию до изменения устройства. Повторное сохранение может использовать ту же ревизию.
- Несовпадение контрольной суммы SHA-256 любого из файлов поколения при валидации вызывает `std::runtime_error("Corrupt or mixed runtime generation")`.
- Деструктор `SaveWorker` корректно пробуждает фоновый поток, завершает выполнение очереди и выполняет `join` без выброса исключений.
- Операции файлового протокола проверяют ошибки. Прерываемые системные вызовы повторяются при `EINTR`. В Linux `close` освобождает дескриптор даже при `EINTR`.

## Потокобезопасность и завершение

- Основной поток реактора готовит срез данных в RAM, вызывает `sqlite3_backup` и передаёт готовый `Snapshot` в очередь воркера.
- Воркер выполняет блокирующий дисковый I/O в отдельном потоке `std::thread`.
- Взаимодействие между потоками синхронизируется через `std::mutex`, `std::condition_variable` и уведомления через неблокирующий `EventPipe`.
- При штатном завершении (`exit`, EOF, `SIGINT`, `SIGTERM`) основной поток ждёт слот, ставит финальный актуальный снимок в конец очереди и вызывает `SaveWorker::stop()` для завершения очереди. Результат финальной попытки определяет успешность сохранения.

## Границы

- Модуль управляет долговечностью файлов состояния, фоновой очередью сохранения и проверкой целостности поколений.
- Модуль НЕ выполняет командную диспетчеризацию устройств (ответственность `execution`).
- Модуль НЕ хранит живые цифровые двойники устройств в памяти (ответственность `devices`).
- Модуль НЕ строит граф онтологии (ответственность `ontology`).

## Критерии приёмки

- Успешная сборка статической библиотеки `SmartHome::Persistence`.
- Корректная фиксация поколения с атомарной заменой `CURRENT`.
- Восстановление состояния из зафиксированного поколения с проверкой SHA-256.
- Прерывание процесса на этапах публикации оставляет целое старое или новое поколение. Устойчивость к физическому отключению питания проверяется отдельно на целевом носителе.
- При исчерпании `capacity` запрос на резервирование возвращает пустой токен.
- Все тесты `runtime_persistence_tests` и `runtime_failures_tests` успешно проходят.
