# Регистрация и восстановление устройств

ID: DeviceManagement

## Цель

Связать инвентарь, фабрики и активные драйверы: регистрировать обнаруженные
устройства и восстанавливать их по сохранённым записям. Спецификация описывает
текущий `DeviceManager` модуля `device_management`, без будущей интеграции ontology.

## Требования

- DM-001: Конструктор получает `IDeviceStorage`, `DriverFactoryRegistry`
  и `DeviceRegistry` по ссылкам, без запуска регистрации или восстановления.
  Зависимости живут дольше менеджера; активными драйверами владеет registry.
- DM-002: `registerDiscoveredDevice(physical_id, driver_id, default_name)`
  создаёт отсутствующие inventory record и активный драйвер, возвращая
  собственную копию `DeviceRecord`. Повторный вызов сохраняет ID, имя
  и существующий драйвер с его текущими значениями.
- DM-003: `restoreStoredDevices()` создаёт отсутствующие активные драйверы
  по записям storage и возвращает число добавленных. Инвентарь не изменяется;
  пустое хранилище и повторное полное восстановление дают `0`.

## Данные и регистрация

`DeviceRecord` содержит `local_id`, `physical_id`, `driver_id`, `name`.
Запись ищется по паре `(physical_id, driver_id)`, активный драйвер — по
`local_id`. ID назначает storage; проверки строк делегируются зависимостям.
`default_name` применяется только при вставке, существующее имя не обновляется.

Сначала проверяется фабрика, затем находится или вставляется запись.
Если активного драйвера нет, вызывается `factory.create(record)` и результат
передаётся в registry через `unique_ptr`. Уже активный драйвер не заменяется,
но наличие фабрики проверяется при каждом вызове регистрации.
Соответствие ID и свойств созданного драйвера записи отдельно не проверяется;
за корректное создание отвечает фабрика.

## Восстановление

Менеджер читает `storage.getAll()` и пропускает уже активные ID без проверки
их фабрик и свойств. Остальные драйверы сначала создаются во временном наборе,
затем последовательно добавляются в registry. Ошибка подготовки уничтожает
временный набор, не добавляя новых драйверов и не затрагивая ранее активные.
Эта гарантия не распространяется на сторонние эффекты пользовательских фабрик.

## Ошибки и согласованность

Неизвестная фабрика при регистрации даёт `UnsupportedDriverError`
(наследник `invalid_argument`) до обращения к storage. При восстановлении
отсутствующего драйвера неизвестная фабрика даёт `runtime_error`.
Возврат `nullptr` фабрикой даёт `logic_error`; исключения зависимостей
пробрасываются без перехвата и без продолжения восстановления.

Общей транзакции нет. Ошибка создания или добавления драйвера после вставки
inventory record оставляет запись в storage. Повторная регистрация использует
её и снова пытается создать отсутствующий драйвер. Ошибка добавления части
подготовленного набора при восстановлении не откатывает уже добавленные драйверы.

Собственных потоков и синхронизации нет; вызывающий код сериализует доступ.
Успешное восстановление логируется на Info, регистрация — на Debug с DeviceId,
включая повторные вызовы. Ошибки обрабатывает вызывающий код;
менеджер не настраивает глобальную logging-сессию.

## Границы

Discovery выполняется отдельным `DiscoveryService`: он вызывает менеджер
и обрабатывает `UnsupportedDriverError` для отдельного устройства; другие
ошибки регистрации распространяются наружу. Ontology, комнаты и capability
links пока поддерживаются в `main.cpp` через `completeGraph()` и `validateGraph()`.
Сохранённые значения возможностей восстанавливает runtime с помощью фабрик
и `CommandDispatcher`; менеджер не хранит reported/desired state.
Переименование, удаление, смена драйвера, учёт доступности, ревизии,
фиксация поколений и MQTT-события не входят в текущий API.

## Критерии приёмки

- Первая регистрация создаёт одну запись и один доступный по ID драйвер.
- Повторная регистрация сохраняет запись и не дублирует активный драйвер.
- Неизвестный драйвер отклоняется без изменения инвентаря.
- Восстановление сохраняет ID и имена, повторное возвращает `0`.
- Неизвестная фабрика при подготовке набора не добавляет его часть в registry.
- Повторный scan не создаёт дублей; неподдерживаемое устройство не мешает остальным.

Существующие проверки: [DeviceManagerTests.cpp](../../tests/DeviceManagerTests.cpp)
и [DiscoveryServiceTests.cpp](../../tests/DiscoveryServiceTests.cpp).
Сценарии `nullptr`, отказа фабрики после вставки и ошибки добавления в registry
этими тестами отдельно не покрыты.
