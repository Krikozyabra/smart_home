# Инвентарь устройств

ID: Storage

## Цель

Хранить идентичность устройств и привязки к драйверам через единый
`IDeviceStorage`. Спецификация описывает текущий модуль `storage`
(`SmartHome::Storage`): реализации в памяти и SQLite.
Реализованы атомарный dump SQLite и необязательный финальный автодамп
при уничтожении хранилища (ST-004–ST-006).

## Требования

- ST-001: `insert(physical_id, driver_id, name)` создаёт запись с назначенным
  хранилищем `DeviceId` и возвращает её копию. Пара `(physical_id, driver_id)`
  уникальна; повторная вставка даёт `invalid_argument`, без обновления записи.
- ST-002: `findByPhysicalId(physical_id, driver_id)` возвращает копию записи
  или `nullopt`. Один physical ID с разными driver ID обозначает разные записи.
- ST-003: `getAll()` возвращает собственный вектор всех записей;
  изменение результата не меняет storage. Общий интерфейс не гарантирует порядок.
- ST-004: `SQLiteDeviceStorage::dumpToFile(path)` синхронно сохраняет
  согласованный снимок открытой SQLite-базы в отдельный файл.
  Снимок сохраняет схему, записи, локальные ID и состояние AUTOINCREMENT.
- ST-005: Публикация снимка выполняется атомарной заменой файла.
  Успех подтверждается только после синхронизации файла и каталога.
- ST-006: При заданном `dump_path` деструктор выполняет финальный атомарный
  dump перед закрытием рабочей базы. Ошибка автодампа не выходит из деструктора
  исключением и сообщается через диагностику.
- ST-007: `IDeviceStorage::dumpToFile(path)` предоставляет сохранение через
  общий интерфейс. SQLite выполняет описанный ниже атомарный dump;
  InMemoryDeviceStorage сообщает `logic_error`, не открывая и не меняя файлы.

## Данные и проверки

`DeviceRecord` содержит `local_id` (`int64_t`), `physical_id`, `driver_id`
и `name`. Сравнение записей учитывает все поля. Пустые physical ID и driver ID
при поиске и вставке дают `invalid_argument`; пустое имя допускается.
Проверки существования фабрики, возможностей и физического устройства нет.
Переполнение счётчика ID в реализации в памяти отдельно не обрабатывается.

## Хранилище в памяти

`InMemoryDeviceStorage` создаётся пустым и хранит записи в RAM.
ID начинаются с `0` и увеличиваются после успешной вставки.
`getAll()` обходит записи по составному строковому ключу.
Данные не сохраняются в файл; новый объект начинает с пустого инвентаря.
Вызов `dumpToFile(path)`, включая вызов через `IDeviceStorage`, всегда даёт
`logic_error`: реализация не поддерживает файловый формат снимка. Путь не
проверяется, файлы и записи хранилища не меняются.

## SQLite и завершение

`SQLiteDeviceStorage(path)` открывает или создаёт базу по переданному пути
и создаёт отсутствующую таблицу `devices`. Колонки: `local_id INTEGER PRIMARY
KEY AUTOINCREMENT`, непустые `physical_id` и `driver_id`, `name NOT NULL`,
уникальность пары идентификаторов. В новой обычной базе первый ID положительный;
совпадение последовательности ID с реализацией в памяти не требуется.

Запросы используют связанные параметры. Существующие записи и ID сохраняются
после закрытия и повторного открытия файловой базы. `getAll()` выполняется без
`ORDER BY`; автоматической миграции или полной проверки существующей схемы нет.
Расположение файла определяет носитель: модуль сам не выбирает RAM, SD или SSD.

Ошибки открытия, схемы, подготовки, привязки и выполнения SQL дают
`runtime_error`; дубликат пары даёт `invalid_argument`, неожиданный NULL
в текстовых полях при чтении — `runtime_error`.
Частично открытое соединение освобождается при ошибке конструктора.
Объект владеет соединением, не копируется и закрывает его в деструкторе.
Перед закрытием выполняется автодамп по заданному `dump_path`.
Публичного `close()` с сообщением об ошибке закрытия нет.

## Сохранение и согласованность

Обычные операции SQLite изменяют открытую базу непосредственно, без отдельной
публичной сессии транзакций или настройки journal/synchronous со стороны модуля.
Успех `insert()` не означает выполнения отдельного dump или сохранения
полного поколения runtime.

### Атомарный dump в файл

Общий интерфейс объявляет `virtual void dumpToFile(const std::string &path) = 0`.
Формат и гарантии публикации определяет реализация; неподдерживаемая операция
даёт `logic_error` без изменения файлов. Для SQLite вызов через `IDeviceStorage`
имеет тот же контракт, что и вызов через конкретный класс.

`SQLiteDeviceStorage::dumpToFile(const std::string &path)` сохраняет
всю базу `main`, включая дополнительные таблицы вызывающего кода.
Формат результата — самостоятельная SQLite-база, а не текст SQL.
Источник может находиться в памяти или в файле. Открытие результата
через `SQLiteDeviceStorage(path)` восстанавливает инвентарь с прежними ID.

Операция не меняет рабочую базу и не переключает соединение на файл
назначения. Последующие изменения источника не меняют опубликованный снимок.

Пустой путь, путь с NUL, ссылка или не обычный файл в качестве назначения,
а также совпадение назначения с рабочей базой, включая файловые
псевдонимы, дают `invalid_argument`. Отсутствующий файл назначения допускается.
Родительский каталог должен существовать; автоматически он не создаётся.

Протокол рассчитан на Linux и локальную файловую систему,
поддерживающую атомарный rename и fsync:

1. Создать уникальный временный файл в каталоге назначения.
2. Сформировать в нём согласованную SQLite-базу через SQLite backup API.
   Простое копирование открытого файла базы и его журналов запрещено.
3. Завершить backup и закрыть временную базу с проверкой ошибок.
   Результат не должен зависеть от внешних WAL/journal-файлов.
4. Выполнить fsync временного файла.
5. Атомарно переименовать его в файл назначения, заменяя прежний снимок.
6. Выполнить fsync родительского каталога, затем вернуть успех.

До переименования ошибка сохраняет прежний файл назначения неизменным;
при первом dump файл назначения остаётся отсутствующим.
После переименования, но до успешного fsync каталога, долговечность
замены неопределённа: операция сообщает об ошибке, даже если новый
файл уже виден. Откат к прежнему файлу не гарантируется.

Ошибки backup, записи, закрытия, синхронизации и переименования дают
`runtime_error` с указанием этапа. Рабочая база остаётся доступной;
после устранения причины dump можно повторить. Собственные временные
файлы удаляются при обработанной ошибке, насколько это возможно,
без подмены исходной ошибки ошибкой очистки. После аварии временные
файлы могут остаться; они не считаются опубликованными снимками.

Вызывающий код сериализует обращения к источнику на время dump
и обеспечивает исключительный доступ к назначению: параллельные
писатели и открытые SQLite-соединения к заменяемому файлу не допускаются.
Назначение не должно иметь внешних WAL/journal-файлов.
Встроенные mutex, межпроцессная блокировка и фоновый worker не добавляются.

### Автодамп при завершении

Контракт конструктора — `SQLiteDeviceStorage(database_path, dump_path = {})`.
Непустой `dump_path` задаёт назначение финального dump; пустой отключает
автодамп и сохраняет поведение существующих вызовов конструктора.
Путь фиксируется относительно текущего каталога при создании объекта
и проверяется на недопустимое назначение по тем же правилам, что явный dump.
Ресурсы назначения открываются только при сохранении.
Явный `dumpToFile(path)` не изменяет настроенный `dump_path`.

Деструктор при включённом автодампе выполняет одну попытку сохранения
по тому же атомарному протоколу, затем освобождает соединение и ресурсы
независимо от результата. Ошибка перехватывается и однократно сообщается
через существующий logging; деструктор остаётся `noexcept`.
Для получения ошибки сохранения вызывающий код использует явный
`dumpToFile()` до уничтожения объекта. Явный dump не отменяет финальный:
после него рабочая база могла измениться.

Перед уничтожением объекта вызывающий код завершает все обращения
к нему и сохраняет исключительный доступ к назначению до окончания
автодампа. Аварийное завершение процесса или отключение питания
не гарантируют вызов деструктора и финальное сохранение.
Автоматического dump после insert или по таймеру нет.
Автодамп настраивается только у SQLiteDeviceStorage; общий интерфейс
предоставляет явный dump, а InMemoryDeviceStorage не выполняет автодамп.

В текущем runtime SQLite открыта в RAM-workspace. Согласованную
публикацию SQLite вместе с ontology через поколения и `CURRENT`
выполняет `main.cpp`. Отдельный dump или автодамп не подтверждает
сохранение полного состояния runtime и не заменяет его протокол публикации.
Общей транзакции с registry или ontology модуль не предоставляет.

## Границы

Модуль не хранит значения возможностей, reported/desired state, доступность,
комнаты или связи ontology. Таблица `runtime_values` создаётся runtime
в той же SQLite-базе, но не относится к API инвентаря. Созданием драйверов
управляет `DeviceManager`. Переименование, удаление, поиск по local ID,
смена драйвера и автоматическое восстановление после сбоя в API отсутствуют.
Собственных потоков и mutex нет; вызывающий код сериализует обращения.

## Критерии приёмки

- Новое хранилище пусто; поиск отсутствующей пары возвращает `nullopt`.
- Вставка возвращает запись с ID, поиск и `getAll()` находят её.
- Разные driver ID с одним physical ID получают отдельные записи и ID.
- Повторная пара и пустые идентификаторы отклоняются.
- SQLite сохраняет записи и ID после повторного открытия файла.
- Dump SQLite доступен через ссылку или указатель на `IDeviceStorage`.
- Dump InMemoryDeviceStorage через общий интерфейс даёт `logic_error`,
  не создаёт и не меняет файлы и сохраняет записи в RAM.
- Имена с кириллицей и апострофами передаются через SQL-параметры.
- Снимки пустой и заполненной базы открываются независимо от источника.
  Сохраняются все таблицы, записи, ID и состояние AUTOINCREMENT.
- Изменения источника после dump не меняют опубликованный файл;
  повторный dump публикует новое состояние.
- Dump из RAM и файловой базы создаёт самостоятельный файл
  без зависимости от журналов источника.
- Некорректные назначения отклоняются без изменения рабочей базы.
- Управляемые отказы до rename сохраняют прежний файл побайтно;
  ошибка fsync каталога после rename не подтверждается как успех.
- Аварийное завершение на этапах публикации не делает частичный
  снимок доступным под окончательным именем. Проверки процесса
  не заменяют отдельную проверку устойчивости к потере питания.
- Деструктор при заданном `dump_path` сохраняет последние изменения,
  в том числе сделанные после явного dump. Без `dump_path` автодампа нет.
- Смена текущего каталога после создания объекта не меняет назначение
  автодампа; явный dump в другой файл также не меняет его.
- Ошибка автодампа даёт одну диагностическую запись, не выпускает
  исключение из деструктора и не препятствует освобождению соединения.

Существующие проверки: [StorageTests.cpp](../../tests/StorageTests.cpp)
и [SQLStorageTests.cpp](../../tests/SQLStorageTests.cpp).
[SQLiteDumpTests.cpp](../../tests/SQLiteDumpTests.cpp) проверяет dump из RAM
и WAL-базы, самостоятельность снимка, схему и дополнительные таблицы,
AUTOINCREMENT, недопустимые назначения, финальный автодамп и его диагностику.
Проверяются вызовы dump через общий интерфейс для SQLite и InMemoryDeviceStorage.
Управляемые отказы проверяют сохранение прежних байтов до rename, очистку
временных файлов и сообщение об ошибке после rename. Отдельный процесс
аварийно выходит на этапах публикации без вызова деструкторов.
Эти проверки не подтверждают устойчивость к потере питания; отдельных
проверок исчерпания ID и всех отказов SQLite нет.
