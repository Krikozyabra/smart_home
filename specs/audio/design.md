# Технические решения модуля audio

Статус: решения реализованы; аппаратная проверка на Raspberry Pi ожидается.
Основание: [spec.md](spec.md), staged diff, `AGENTS.md`, реализация и тесты
модулей `oww` и `ontology`. Целевая платформа — Linux, Raspberry Pi 4b.

## 1. Границы и уточнения спецификации

Модуль захватывает звук с одного выбранного устройства в двух режимах:
непрерывно в кольцевой буфер или однократно в PCM-вектор. Данные хранятся
в RAM. Запись WAV, распознавание, интеграция с онтологией и автоматическое
восстановление устройства в область реализации не входят.

Одобренные уточнения формата PCM, снимков, конфликтов режимов, повторного
запуска и ошибок рабочего потока внесены в `spec.md` перед реализацией.

## 2. Архитектура и зависимости

- Пространство имён: `smart_home::audio`.
- Публичные заголовки C++17: `AudioConfig.h`, `AudioTypes.h`,
  `IAudioCapture.h`, `AlsaAudioCapture.h` в `audio/include/audio/`.
- `AudioConfig` содержит неизменяемые после создания настройки;
  `validateConfig()` проверяет их без открытия устройства.
- `IAudioCapture` задаёт контракт захвата. `AlsaAudioCapture` реализует его
  через PIMPL, не раскрывая ALSA и детали синхронизации в публичном API.
- Кольцо и интерфейс источника для тестов остаются в `audio/src/`.
  Тесты могут подставлять источник через приватную фабрику или test access;
  публичных методов управления тестовыми ошибками не будет.

Статическая библиотека `smart_home_audio` с alias `SmartHome::Audio`
публикует каталог `include` и требование C++17. Зависимости `ALSA::ALSA`,
`SmartHome::Logging`, `Threads::Threads` — `PRIVATE`. В CMake используются
`find_package(ALSA REQUIRED)` и `find_package(Threads REQUIRED)`.
Модуль подключается в корневом CMake после logging, до потребителей и tests;
`audio` добавляется в список входов Doxygen. Прямых зависимостей от `oww`
и `ontology` нет. Приложение не начинает захват автоматически.

## 3. Конфигурация и формат

| Поле | Значение по умолчанию | Контракт |
|---|---|---|
| `device_name` | `default` | Имя capture PCM устройства ALSA; непустое, без NUL |
| `sample_rate_hz` | 16000 | Положительная частота, поддерживаемая выбранным PCM |
| `channels` | Mono | Перечисление Mono = 1, Stereo = 2 |
| `frame_duration` | 80 мс | Положительное целое число миллисекунд |
| `buffer_capacity_frames` | 125 | Положительное число полных кадров кольца |

PCM представлен `std::vector<std::int16_t>`: signed PCM16 в порядке байтов
хоста; для стерео отсчёты чередуются L, R. Один временной отсчёт ALSA
содержит значения всех каналов. Аудиокадр модуля содержит множество таких
отсчётов и не равен одному ALSA frame.

Для длительности `D` мс и частоты `R` число отсчётов на канал равно
`R * D / 1000`. Произведение должно делиться на 1000 без остатка.
Размер PCM-вектора равен этому числу, умноженному на число каналов.
Это правило действует и для кадра кольца, и для разовой записи.
Нулевые и отрицательные длительности отклоняются. Все умножения,
преобразования типов и размеры контейнеров проверяются до выделения памяти;
переполнение и недопустимые размеры дают `std::invalid_argument`.
Недостаток памяти не скрывается и может дать `std::bad_alloc`.

Кольцо по умолчанию хранит 10 секунд: 125 × 1280 × 2 = 320000 байт PCM,
без учёта метаданных, рабочего кадра и снимков читателей. Память кольца
и рабочего кадра выделяется до начала непрерывной записи.

## 4. Публичный API

Основные операции реализованного API:

```cpp
using PcmSamples = std::vector<std::int16_t>;

struct AudioFrame {
    std::uint64_t sequence;
    PcmSamples samples;
};

struct AudioSnapshot {
    std::uint64_t session_id;
    std::vector<AudioFrame> frames;
};

class IAudioCapture {
public:
    virtual ~IAudioCapture() = default;
    virtual AudioConfig getConfig() const = 0;
    virtual void startContinuous() = 0;
    virtual void stopContinuous() = 0;
    virtual PcmSamples recordFor(std::chrono::milliseconds duration) = 0;
    virtual AudioSnapshot snapshot() const = 0;
    virtual void rethrowIfFailed() const = 0;
};
```

Реализация не копируется и не перемещается. Публичные заголовки получают
русские Doxygen-комментарии: единицы измерения, владение, допустимая
конкурентность, ошибки и продолжительность жизни объекта. Уничтожать объект
можно только после завершения внешних обращений к нему.

## 5. Захват ALSA

Конструктор проверяет конфигурацию, открывает выбранный capture PCM,
устанавливает interleaved PCM16, каналы и точную частоту. Отсутствующее,
недоступное или занятое устройство, а также невозможность установить
запрошенный формат приводят к `std::runtime_error` с контекстом ALSA.
Частично созданные ресурсы освобождаются через RAII.

Запрошенная частота не подменяется ближайшей незаметно для потребителя.
Модуль не реализует собственный ресемплер; если пользователь выбирает ALSA
plugin PCM, преобразования могут выполняться самим ALSA plugin.

Источник использует неблокирующее чтение и ожидание готовности через poll.
В ожидание включается отдельный дескриптор пробуждения остановки.
Только владелец текущего режима обращается к PCM handle; остановка
сигнализирует ему, а не закрывает handle из другого потока. Короткие чтения
накапливаются до требуемого объёма, EINTR повторяется, EAGAIN возвращает
к ожиданию. Отсутствие прогресса ограничивается внутренним тайм-аутом;
тайм-аут равен 5 с. Целевой допуск остановки на незагруженной системе —
250 мс после сигнала; его соблюдение требует проверки на целевой плате. Активного ожидания быть не должно.

Overrun, suspend, отключение устройства и иные сбои завершают текущую
запись ошибкой. Потерянный звук не заменяется тишиной, разрыв не скрывается.
Обоснование используемых возможностей: [ALSA PCM interface](https://www.alsa-project.org/alsa-doc/alsa-lib/pcm.html)
и [контракт snd_pcm_readi](https://www.alsa-project.org/alsa-doc/alsa-lib/group___p_c_m.html).

## 6. Кольцевой буфер и чтение

Кольцо содержит только полные кадры и ограничено заданной ёмкостью.
Единственный писатель — рабочий поток непрерывного захвата. Сначала он
собирает полный кадр вне блокировки кольца, затем публикует его под mutex.
При заполнении перезаписывается самый старый кадр. Незавершённый кадр
при остановке или ошибке отбрасывается.

`snapshot()` под mutex копирует согласованное содержимое в порядке
от старого к новому. Возвращаются собственные данные: чтение не удаляет
кадры, ссылки и указатели во внутреннее хранилище не выдаются. Читать
можно из нескольких потоков, во время записи, после остановки и после
ошибки. До первого запуска снимок пуст. Обработка снимка выполняется
после освобождения mutex. Стоимость копирования зависит от настроенной
ёмкости; это осознанный выбор простой реализации для исходного объёма.

Каждый успешный новый запуск очищает кольцо и получает новый `session_id`.
Внутри сеанса `sequence` последовательно возрастает от нуля. По последнему
обработанному номеру читатель исключает дубликаты и обнаруживает пропуск
из-за перезаписи; смена сеанса означает новый поток аудио. Переполнение
счётчиков не должно приводить к повторной выдаче идентификаторов:
достижение предела завершается явной ошибкой.

## 7. Режимы, синхронизация и завершение

Состояния: Idle, Continuous, OneShot, Failed. Управляющие операции
сериализуются отдельным lifecycle mutex. Доступ к кольцу и к сохранённой
ошибке синхронизируется отдельно. Блокировка кольца не удерживается
во время чтения ALSA, ожидания событий или join.

| Операция | Idle | Continuous | OneShot | Failed |
|---|---|---|---|---|
| `startContinuous()` | Запустить worker и новый сеанс | Успешный повтор без очистки | `logic_error` | Повторить сохранённую ошибку |
| `recordFor(D)` | Выполнить синхронную запись | `logic_error` | `logic_error` | Повторить сохранённую ошибку |
| `stopContinuous()` | Успешный повтор | Пробудить и join | `logic_error` | Присоединить worker, если нужен, и повторить ошибку |
| `snapshot()` | Снимок | Снимок | Последний снимок кольца | Последний снимок кольца |

`recordFor()` захватывает состояние OneShot под lifecycle mutex, затем
отпускает его на время чтения. Конкурирующие запросы видят занятый режим
и отклоняются, а не ожидают его завершения для неявного запуска.
Другой `stopContinuous()` во время остановки ожидает её завершения;
после успешной остановки он также завершается успешно.

Разовая запись возвращает ровно вычисленное число PCM-значений, включая
последний фрагмент короче кадра кольца, и не меняет кольцо. Длительность
определяется количеством аудиоотсчётов; время вызова может быть больше
из-за запуска устройства и планирования ОС. Частичный результат при
ошибке не возвращается. После успеха состояние снова Idle; при сбое
захвата — Failed. Ошибки аргументов не переводят объект в Failed.

Рабочий поток перехватывает все исключения, сохраняет `std::exception_ptr`
и переводит объект в Failed. Необработанное исключение не выходит
из функции потока. Ошибка доступна через `rethrowIfFailed()` и явную
остановку; чтение ошибки не очищает её. При неудаче создания worker
ресурсы и состояние откатываются, объект остаётся Idle.

Деструктор сигнализирует остановку, присоединяет поток и освобождает ALSA
без выбрасывания исключений. После сбоя захвата для продолжения нужен новый
экземпляр. Захваченная ошибка логируется один раз на границе обработки
вызывающей стороной; модуль не логирует её при каждом повторном выбрасывании.
Деструктор может сообщить об оставленной без обработки ошибке один раз
через существующий Logging. Сырые аудиоданные в журнал не попадают.

## 8. Совместимость с существующими модулями

Как в `oww`, внешний SDK скрыт за PIMPL, публичный API остаётся C++17,
а ошибки выражаются стандартными исключениями. Как в `ontology`,
многопоточные операции возвращают собственные копии данных, остановка
worker предшествует освобождению ресурсов, а внедрение ошибок для тестов
остаётся приватным.

`oww::IOpenWakeWord` принимает строго 1280 signed PCM16 отсчётов моно
на частоте 16000 Гц. Настройки audio 16000/Mono/80 мс дают этот формат
без преобразования. Потребитель проверяет настройки и размер каждого
кадра перед передачей указателя в `processFrame()`: детектор длину
не проверяет. Кадры одного сеанса обрабатываются последовательно одним
экземпляром детектора вне блокировки кольца. При смене сеанса или пропуске
кадров детектор пересоздаётся, чтобы не продолжать несогласованный контекст.
Произвольные настройки audio не считаются совместимыми с oww автоматически.

## 9. Проверка решений

Основные тесты используют детерминированный приватный источник:
заданные PCM, короткие чтения, отсутствие данных, сбой и управляемое
ожидание. Барьеры и condition_variable позволяют проверять гонки
и остановку без произвольных sleep. Проверяются конфигурация,
точное содержимое записей, порядок и переполнение кольца, несколько
читателей, единственный писатель, конфликты режимов, передача исключений
и освобождение ресурсов. Тесты регистрируются в CTest с тайм-аутами.

Реальный ALSA backend проверяется отдельно с явно выбранным микрофоном.
Отсутствие оборудования не подменяется успехом интеграционного теста.
На Raspberry Pi измеряются память, CPU, задержка остановки и способность
потребителя успевать за захватом. Детальная последовательность работ
и критерии готовности приведены в [plan.md](plan.md).
