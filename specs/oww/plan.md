# План реализации модуля OpenWakeWord (oww)

Модуль предназначен для детекции ключевых слов по кадрам аудиопотока с использованием OpenWakeWord, с учетом аппаратных ограничений Raspberry Pi 4b 8/120 (SD-карта, оптимизация потребления памяти и тактов CPU).

---

## 1. Анализ требований и особенности реализации

### 1.1. Требования спецификации (`specs/oww/spec.md`)
- **OWW-001**: Система хранит путь к модели; проверка существования файла модели выполняется при создании системы (критерий приёмки).
- **OWW-002**: Система предоставляет функцию, принимающую аудиокадр длительностью 80 мс.
- **Границы**: Функция возвращает число с плавающей точкой в диапазоне от `0.0` до `1.0` (OWW-002; опечатка со ссылкой на OWW-001 исправлена в спецификации).
- **Требование к валидации длины**: Согласно указаниям, проверка длины входного аудиоблока в функции обработки не выполняется.

### 1.2. Технические решения (`specs/oww/design.md`)
- **Использование OpenWakeWord**: Выбран CPU ONNX Runtime и три ONNX-модели: спектрограмма, акустические признаки и бинарный классификатор ключевого слова. TFLite не поддерживается. Для «Нафани» найден публичный классификатор сообщества; загрузчик и источники описаны в `oww/models/README.md`.
- **Оптимизация под Raspberry Pi 4b**:
  - Инициализация и прогрев моделей OpenWakeWord при создании экземпляра, исключение повторных загрузок с SD-карты.
  - Предварительное выделение внутренних тензоров и рабочих буферов признаков, предотвращение динамических аллокаций памяти в цикле обработки кадров.
  - Настройка ограничения количества потоков инференса для снижения нагрузки на CPU.

## 2. Архитектура и компоненты модуля

### 2.1. Конфигурация (`OwwConfig`)
Файлы: `oww/include/oww/OwwConfig.h`, `oww/src/OwwConfig.cpp`
- Структура конфигурации:
  - `model_path`: путь к файлу модели OpenWakeWord (`std::string`).
  - `sample_rate_hz`: частота дискретизации аудио (`16000` Гц по умолчанию).
  - `inference_threads`: количество потоков инференса (по умолчанию `1` для Raspberry Pi).
  - `melspec_model_path`, `embedding_model_path`: пути к общим моделям. Пустые значения означают поиск `melspectrogram.onnx` и `embedding_model.onnx` рядом с классификатором.
- Валидация конфигурации:
  - Проверка непустого пути.
  - Проверка физического существования обычных файлов всех трёх моделей через `std::filesystem::is_regular_file` (OWW-001). При отсутствии файла выбрасывается исключение `std::invalid_argument`.
  - Поддерживается только 16000 Гц и положительное число потоков инференса.

### 2.2. Публичный интерфейс (`IOpenWakeWord`)
Файл: `oww/include/oww/IOpenWakeWord.h`
- Чисто виртуальный интерфейс с русской документацией Doxygen:
  - `virtual ~IOpenWakeWord() = default;`
  - `virtual const std::string& getModelPath() const noexcept = 0;`
  - `virtual float processFrame(const std::int16_t* pcm_frame) = 0;` (со вспомогательными перегрузками для `PcmFrame = std::array<int16_t, 1280>` и `const std::vector<int16_t>&`).
  - Первоначальный `std::span` заменён указателем с фиксированным контрактом кадра: `std::span` требует C++20 и противоречил требованию C++17. Вызывающая сторона обеспечивает доступность 1280 отсчётов; размер не проверяется.
  - Возвращаемое значение: вероятность детекции ключевого слова в диапазоне `[0.0f, 1.0f]`. Без валидации длины входного буфера.

### 2.3. Реализация детектора (`OpenWakeWordDetector`)
Файлы: `oww/include/oww/OpenWakeWordDetector.h`, `oww/src/OpenWakeWordDetector.cpp`
- Реализация интерфейса `IOpenWakeWord` с использованием паттерна PIMPL (`OpenWakeWordDetector::Impl`):
  - Сокрытие деталей OpenWakeWord и runtime инференса от пользователей публичных заголовков.
  - Проверка существования модели в конструкторе.
  - Инференс OpenWakeWord над переданными аудиоданными.

## 4. Интеграция в сборочную систему

1. **`oww/CMakeLists.txt`**:
   - Определение библиотеки `smart_home_oww` (статическая) с псевдонимом `SmartHome::Oww`.
   - Подключение зависимостей: `SmartHome::Common` публично; `SmartHome::Logging` и ONNX Runtime приватно. `cmake/OnnxRuntime.cmake` поддерживает установленный пакет и SDK с `include/` и `lib/`.
   - Компиляция с флагами `-Wall -Wextra -Wpedantic` и стандартом C++17.
2. **Корневой `CMakeLists.txt`**:
   - Добавление `add_subdirectory(oww)`.
3. **`cmake/Docs.cmake`**:
   - Добавление `oww` в перечень модулей для генерации документации Doxygen (`DOC_INPUTS`).

## 5. План тестирования (`tests/OwwTests.cpp`)

Регистрация исполняемого файла `oww_tests` в `tests/CMakeLists.txt` с использованием `TestUtil.h`:
1. **Тестирование OWW-001 (проверка модели при создании)**:
   - Передача несуществующего пути к модели -> выброс `std::invalid_argument`.
   - Передача существующего валидного комплекта ONNX-моделей -> успешное создание детектора. Повреждённый или несовместимый файл отклоняется.
   - Проверка метода `getModelPath()` на совпадение с переданным значением.
2. **Тестирование OWW-002 и OpenWakeWord инференса**:
   - Передача аудиокадра 80 мс -> вызов пайплайна OpenWakeWord, получение значения вероятности типа `float` в диапазоне от `0.0` до `1.0`.
   - Проверка перегрузок и передачи первых 1280 отсчётов без проверки размера вектора. Неполные/нулевые буферы не передаются, поскольку нарушают предусловие.
   - Проверка полного пайплайна и истории независимым численным эталоном на вычислительных ONNX-графах, с обработкой через настоящий ONNX Runtime.
   - Проверка ошибок типов/форм тензоров, NaN/Infinity и выхода вероятности за диапазон.
3. **Ресурсные тесты**:
   - Автоматический прогон тысяч кадров и независимых экземпляров; проверка под санитайзерами.
   - Отдельный `oww_model_tests` обрабатывает 1000 кадров обученной моделью, если задан `SMART_HOME_OWW_TEST_MODEL`. Замеры памяти/CPU и качества распознавания на Raspberry Pi 4b требуют выбранного комплекта моделей и целевой платы.

## 7. Выполненные проверки и ограничения среды

Из корня проекта выполнены:

```sh
cmake -B /tmp/smart-home-oww/build -S . -DCMAKE_BUILD_TYPE=Debug -DSMART_HOME_LADYBUG_SDK_DIR=/home/prince/Projects/lbdb_test
cmake --build /tmp/smart-home-oww/build -j 4
ctest --test-dir /tmp/smart-home-oww/build --output-on-failure -j 4
cmake --build /tmp/smart-home-oww/build --target docs
```

Сборка успешна, 18/18 тестов проходят, Doxygen HTML собран. Модуль и его
публичный потребитель компилируются с `-std=c++17`. Тестовые ONNX-графы используют
настоящий runtime; тысячи кадров проверяются независимым численным эталоном.
Эти графы не распознают слова и не устанавливаются как рабочие модели.

```sh
cmake -B /tmp/smart-home-oww/asan -S . -DCMAKE_BUILD_TYPE=Debug -DBUILD_DOCS=OFF -DSMART_HOME_LADYBUG_SDK_DIR=/home/prince/Projects/lbdb_test -DSMART_HOME_ONNXRUNTIME_DIR=/usr -DCMAKE_CXX_FLAGS='-fsanitize=address,undefined -fno-omit-frame-pointer'
cmake --build /tmp/smart-home-oww/asan --target oww_tests -j 4
ASAN_OPTIONS=detect_leaks=0 UBSAN_OPTIONS=halt_on_error=1 ctest --test-dir /tmp/smart-home-oww/asan -R '^oww_tests$' --output-on-failure
```

AddressSanitizer и UndefinedBehaviorSanitizer: тест проходит. LeakSanitizer с
`detect_leaks=1` не смог завершить проверку: среда сообщает, что он не работает
под `ptrace`. Проверка утечек не считается выполненной.

`git diff --check` и `clang-format --dry-run --Werror` для новых C++-файлов проходят.
Загрузчик отдельно проверен на локальных `file://`-источниках: содержимое файлов,
повторный запуск и удаление `.part` при ошибке. Это не проверка реальных весов.

Команда `cmake -P oww/DownloadModels.cmake` и отдельная попытка `curl` не смогли
скачать модель при первоначальной реализации: соединение через сетевой прокси
`127.0.0.1` было недоступно. Затем пользователь скачал комплект; его проверка
описана ниже. Проверки качества распознавания на аудиозаписях и ресурсов на
Raspberry Pi пока не выполнены.

### Проверка скачанного комплекта (2026-10-28)

В `oww/models/` найдены `nafanya.onnx` (201 КиБ), `melspectrogram.onnx`
(1,1 МиБ) и `embedding_model.onnx` (1,3 МиБ). Из корня проекта выполнены:

```sh
cmake -B build -S . -DSMART_HOME_OWW_TEST_MODEL=/home/prince/Projects/smart_home/oww/models/nafanya.onnx
cmake --build build --target oww_tests oww_model_tests -j 4
ctest --test-dir build -R '^oww(_model)?_tests$' --output-on-failure -V
```

Сборка успешна, 2/2 тестов проходят. Фактические модели совместимы с модулем:
детектор создаётся и прогревается, все три этапа выполняются. Обработка 1000
кадров по 80 мс (80 секунд синтетического аудио) заняла 1,54 с на текущей машине
после инициализации. Все возвращённые вероятности конечны и лежат в `[0, 1]`.
Это проверка загрузки и вычислений; точность обнаружения произнесённого слова
«Нафаня» и быстродействие на Raspberry Pi этим тестом не проверяются.
