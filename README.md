## Онтология дома (LadybugDB)

Для сборки нужен готовый C/C++ SDK LadybugDB с `include/lbug.hpp` и
`lib/liblbug.a` либо `lib/liblbug.so`. Путь задаётся явно, без зависимости от
расположения соседних проектов:

```sh
cmake -B build -S . -DSMART_HOME_LADYBUG_SDK_DIR=/path/to/ladybug-sdk
cmake --build build -j2
ctest --test-dir build --output-on-failure
cmake --build build --target docs
```

Вместо CMake-параметра можно задать `LADYBUG_SDK_DIR`. Для статического SDK
нужны OpenSSL и Threads. При настройке CMake компилирует, связывает и запускает
проверку выбранных заголовков и бинарной библиотеки. Проверена версия 0.21.2:
реализация требует C++20, а публичные заголовки и приложение остаются C++17.
Несовместимые SDK завершают настройку с диагностикой; автоматической загрузки нет.
Реализация файлового протокола рассчитана на Linux и локальную файловую систему
с `flock`, атомарным `rename` и `fsync`. Кросс-компиляция пока не поддерживается.

`SmartHome::Ontology` содержит узлы `rooms(id STRING, name STRING)`,
`devices(id INT64, name STRING, type STRING)` и
`abilities(id STRING, name STRING, category STRING)` с первичными ключами `id`.
Связи направлены от устройств: `LOCATED_IN -> rooms`, `HAS_FEATURE -> abilities`.
Устройство может находиться только в одной комнате; переназначение выполняется
транзакционно. Повторное добавление возможности не создаёт вторую связь.
Методы `addRoom`, `addDevice`, `addAbility` создают либо обновляют свойства узла,
сохраняя его связи. Удаление узла удаляет его связи, но сохраняет соседние узлы.
Списки возвращаются в порядке ключей. Значения передаются параметрами Cypher.

Ключ устройства совпадает с локальным `DeviceId`; ключ возможности совпадает с
`CapabilityDescriptor::getId()` (`on_off`, `brightness`, `color`, `temperature`).
SQLite / `IDeviceStorage` по-прежнему владеют физическими идентификаторами,
метаданными обнаружения и привязками драйверов. Онтология хранит семантические
узлы и связи, не копирует аппаратные адреса и не выполняет операции с драйверами.
Общей транзакции с SQLite нет: вызывающая сторона сначала сохраняет инвентарь,
затем повторяемо обновляет онтологию и обрабатывает возможный частичный сбой.
Демонстрация в `main()` заполняет комнаты и возможности существующих
симулированных драйверов, запрашивает устройства ванной и сохраняет онтологию.
Пользовательские размещения существующих устройств при повторном запуске сохраняются.

| CLI (также допускается `--имя=значение`) | Переменная окружения | По умолчанию |
| --- | --- | --- |
| `--ontology-path` | `SMART_HOME_ONTOLOGY_PATH` | `data/home_ontology.lbdb` |
| `--ontology-ram-dir` | `SMART_HOME_ONTOLOGY_RAM_DIR` | `/dev/shm` |
| `--ontology-sync-seconds` | `SMART_HOME_ONTOLOGY_SYNC_SECONDS` | `30` |
| `--ontology-allow-disk-fallback` | `SMART_HOME_ONTOLOGY_ALLOW_DISK_FALLBACK` | `0` |

CLI переопределяет проверенные значения окружения. Некорректные параметры или
переменные окружения завершают запуск с кодом 2. Период — целое число от 0 до
31536000 секунд; 0 отключает фоновые снимки. Например:

```sh
./build/bin/smart_home --ontology-path=data/home.lbdb --ontology-sync-seconds=15 --log-level=debug
```

На старте основной файл копируется в приватный каталог с правами 0700 внутри
`/dev/shm`. Движок использует только рабочую копию. Буферный пул по умолчанию —
64 МиБ, число потоков — 2; эти лимиты задаются через `OntologyConfig`.
Перед созданием каталога проверяется запас свободного места (минимум 64 МиБ,
для существующей базы — минимум три размера файла). Это предварительная
проверка, а не резервирование: последующее заполнение tmpfs может вызвать ошибку.
При недоступной RAM запуск завершается с ошибкой. Только явное разрешение
`allow_disk_fallback` / значение `1` допускает временный рабочий каталог рядом
с постоянным файлом; при этом выдаётся предупреждение.

Направление копирования: постоянная база → RAM только на старте, RAM → постоянная
база при `sync()`, периодическом сохранении и `close()`. Первое создание сразу
сохраняет схему. Снимок блокирует запросы, выполняет `CHECKPOINT`, закрывает
соединение и базу, копирует файл во временный файл в каталоге назначения,
выполняет `fsync`, атомарное переименование и `fsync` каталога, затем открывает
RAM-базу снова. Постоянный файл не изменяется обычными запросами.
Протокол основан на [транзакциях и CHECKPOINT Ladybug](https://docs.ladybugdb.com/cypher/transaction/)
и [описании файлов базы](https://docs.ladybugdb.com/developer-guide/files/).

Блокировка отдельного `.lock` удерживается весь срок жизни экземпляра; этот файл
не удаляется, его наличие после остановки нормально. Канонизация путей учитывает
символические ссылки, жёсткие ссылки на базу запрещены. Все писатели должны
соблюдать эту блокировку: параллельно открывать постоянную базу сторонним клиентом
нельзя. WAL/теневые файлы постоянной базы восстанавливаются самим движком до
копирования. Повреждённые базы, несовместимая схема и ошибки воспроизведения WAL
не приводят к автоматическому созданию пустой базы.

При ошибке до переименования предыдущий постоянный снимок сохраняется. Ошибка
после переименования означает неопределённость сохранения метаданных на носителе;
её можно устранить повторным `sync()`. Фоновый поток логирует ошибку и повторяет
попытку через заданный период. `close()` останавливает и присоединяет поток и
сообщает об ошибке финального сохранения исключением; после исправления причины
можно повторить `close()`. Деструктор выполняет последнюю попытку без исключений.
При её неудаче рабочие файлы сохраняются для ручного восстановления. Неудачное
повторное открытие движка блокирует дальнейшие запросы; постоянный снимок и
рабочие файлы сохраняются до успешного закрытия/восстановления.

При аварийном завершении теряются изменения после последнего успешного снимка.
Обычно это до 30 секунд плюс длительность сохранения; при сбоях синхронизации
интервал потерь увеличивается. Оставшиеся RAM-каталоги не восстанавливаются
автоматически и не заменяют постоянную базу. Проверив, что процесс завершён,
администратор может сохранить или удалить их вручную. Остатки собственных
временных файлов постоянного снимка удаляются при следующем старте под блокировкой.

Новые CTest-наборы: `ontology_config_tests`, `ontology_storage_tests`,
`ontology_sync_tests`, `ontology_concurrency_tests`. Они используют реальный SDK,
изолированные временные каталоги и управляемые точки отказа. Проверяются связи,
параметры, перезапуск, атомарность, восстановление WAL после аварийного выхода,
межпроцессная блокировка и конкурентная работа с фоновым сохранением.
Дополнительная проверка `/dev/shm` внутри набора конфигурации явно пропускается,
если среда запрещает запись туда; остальные проверки выполняются в изолированной
настраиваемой рабочей директории. Глобальные настройки/данные приложения не используются.

## Диагностическое логирование

Для сборки требуется пакет разработки spdlog (`find_package(spdlog CONFIG)`).
Если пакет не установлен, включите загрузку закрепленной версии v1.17.0:
`cmake -B build -S . -DSMART_HOME_FETCH_SPDLOG=ON` (требуется доступ к GitHub и Git).

Логирование синхронное и потокобезопасное. Диагностика выводится в stderr и
`logs/smart_home.log`, относительно текущего рабочего каталога. Измерения остаются
в stdout. Порог по умолчанию — INFO; файл ротируется при 5 МиБ, сохраняются три
архивных файла плюс текущий. Отдельная запись больше порога может превысить его.

```sh
./build/bin/smart_home --log-level=debug --log-file=logs/smart_home.log
./build/bin/smart_home --log-level=off --log-file=
```

| CLI | Переменная окружения | Значение по умолчанию |
| --- | --- | --- |
| `--log-level` | `SMART_HOME_LOG_LEVEL` | `info` |
| `--log-file` | `SMART_HOME_LOG_FILE` | `logs/smart_home.log` |
| `--log-max-size-mib` | `SMART_HOME_LOG_MAX_SIZE_MIB` | `5` |
| `--log-max-files` | `SMART_HOME_LOG_MAX_FILES` | `3` |

Приоритет для каждого поля: CLI > окружение > значения по умолчанию. Поддерживаются
формы `--ключ=значение` и `--ключ значение`; при повторении действует последнее
значение. Пустой путь отключает файловый вывод. Размер должен быть положительным,
число архивов — от 1 до 200000. Неизвестные аргументы и некорректные значения CLI
дают код выхода 2 до выполнения команд. Некорректное окружение вызывает
предупреждение и заменяется значением по умолчанию.

Уровни, без учета регистра: TRACE (трассировка), DEBUG (отладка), INFO (жизненный
цикл), WARN (обработанное отклонение), ERROR (ошибка операции с продолжением),
CRITICAL (фатальное завершение), OFF (отключение обычных записей). DEBUG и TRACE
доступны и в Release. Ошибка записывается один раз в месте обработки; физические
адреса и произвольный текст исключений в диагностику не копируются.

При невозможности открыть файл сохраняется вывод в stderr. Ошибки приемников
вызывают прямое предупреждение в stderr, не чаще одного раза за пять секунд,
и не меняют исключения бизнес-логики. Служебные сообщения об ошибках самого
логирования могут выводиться при OFF. До инициализации и после завершения WARN
и выше выводятся минимальным обработчиком в stderr. Инициализацией и завершением
владеет `main`; библиотеки не меняют глобальный реестр spdlog.

## MQTT-клиент

Модуль `SmartHome::Mqtt` использует C++ библиотеку Mosquitto (`libmosquittopp`) и
поддерживает MQTT 3.1.1. Для сборки нужны `pkg-config` и пакеты разработки
`libmosquittopp` и `libmosquitto` версии 2.0 или новее. На Arch/Manjaro они входят
в `mosquitto`; на Debian/Ubuntu установите `libmosquittopp-dev libmosquitto-dev`.
Библиотека находится через pkg-config; для отдельной установки задайте
`PKG_CONFIG_PATH`. Загрузка исходников при конфигурации не выполняется.

Публичный интерфейс — `mqtt/interfaces/IMqttClient.h`, реализация —
`mqtt/MosquittoClient.h`. В публичных заголовках нет типов Mosquitto.
Клиент отправляет бинарные сообщения через `publish`, принимает их после
`subscribe` через неблокирующий `tryRead` или `readFor` с тайм-аутом.
Тема и данные входящего `MqttMessage` принадлежат сообщению; нулевые байты и
пустая полезная нагрузка допустимы. Темы, форматы данных и тип брокера задаёт
вызывающий код. Связь с драйверами и диспетчером команд пока не задаётся.

```cpp
#include "mqtt/MosquittoClient.h"
#include <chrono>

using namespace smart_home::mqtt;
using namespace std::chrono_literals;

MqttConfig config;
config.host = "127.0.0.1"; // Замените адресом своего брокера.
config.port = 1883;
MosquittoClient client;
client.connect(config); // Ожидает успешный CONNACK.
auto subscription = client.subscribe("example/bytes", MqttQoS::AtLeastOnce);
if (client.waitForOperation(subscription, 2s).status != MqttOperationStatus::Completed)
    throw MqttException("Subscription failed or timed out.");
auto publication = client.publish("example/bytes", {0, 1, 255}, MqttQoS::AtLeastOnce);
if (!client.waitForDelivery(publication, 2s))
    throw MqttException("Publish failed or timed out.");
MqttMessage message;
if (client.readFor(2s, message)) {
    // Используйте message.topic и message.payload в потоке приложения.
}
client.disconnect();
```

`publish`, `subscribe` и `unsubscribe` возвращают собственный токен операции.
Возврат означает принятие запроса библиотекой. `waitForOperation` различает
`Pending`, `Completed`, `Rejected`, `Cancelled` и `Unknown`; для SUBACK возвращает
разрешённый QoS. Терминальный результат читается один раз и освобождает место
для следующей операции. После тайм-аута `Pending` токен остаётся действительным:
ожидание можно повторить. `waitForDelivery` — сокращённая проверка `Completed`.
Для QoS 0 это отправка, для QoS 1 — PUBACK, для QoS 2 — PUBCOMP; подтверждение
не означает выполнение команды другим приложением. MQTT 3.1.1 не предоставляет
отрицательный PUBACK для проверки прав публикации.

`MqttConfig` задаёт обязательный host, порт, clientId, cleanSession, keepalive,
тайм-аут CONNACK, задержки переподключения и лимиты ресурсов. По умолчанию:

| Параметр | Значение |
| --- | --- |
| Порт / keepalive / cleanSession | 1883 / 60 с / true |
| connectTimeout | 5 с ожидания CONNACK |
| reconnectDelayInitial / reconnectDelayMax | 1 с / 30 с, экспоненциальный рост |
| receiveQueueCapacity / receiveQueueBytes | 1000 сообщений / 16 МиБ темы и данных |
| maxPayloadBytes / maxPendingPublishBytes | 16 МиБ / 16 МиБ до подтверждений |
| maxPendingOperations | 256 токенов, включая непрочитанные результаты |
| maxSubscriptions | 128 фильтров, включая сохранённые намерения отписки |

При переполнении входящей очереди отбрасывается новое сообщение; уже принятые
сохраняют FIFO. `droppedMessages()` показывает потери после последнего `connect`.
Предупреждение ограничено одним сообщением за пять секунд. При превышении лимита
исходящих операций выбрасывается `MqttException`. Обязательно читайте результаты
всех своих токенов, включая подписки и отписки. Сетевые callback не вызывают
пользовательский код и не выводят адреса, темы, пароли или содержимое сообщений.

При потере соединения состояние становится `Connecting`; после переподключения
повторяются подписки и намерения отписки, а библиотека может повторить публикации
QoS 1/2. Запросы при отсутствии соединения отклоняются. Отказ CONNACK, ошибка
авторизации, TLS или протокола прекращают автоматические попытки. После неудачного
первоначального подключения клиент очищает транспорт; `connect` можно повторить.
Для запущенного клиента сначала вызовите `disconnect`.

Пароль задаётся через `config.username` и `config.password`. TLS включается
через `config.tls`: необходим `caFile`, а для взаимной авторизации —
`clientCertFile` и `clientKeyFile` без парольного шифрования. По умолчанию
`verifyPeer=true` проверяет сертификат и имя брокера. Порт библиотеки задаётся
явно, например 8883; включение TLS в конфигурации не переписывает порт.
Для постоянной сессии `cleanSession=false` требуется непустой `clientId`.

Методы потокобезопасны; операции управления соединением сериализованы.
`disconnect` будит ожидающих читателей, отменяет неподтверждённые операции и
присоединяет сетевой поток до уничтожения транспорта. Оставшиеся сообщения
можно дочитать; следующий `connect` очищает очередь и старые токены.
Глобальная библиотека инициализируется до создания транспорта и освобождается
после уничтожения последнего клиента. Перед уничтожением клиента завершите
свои потоки, обращающиеся к нему; перемещение также требует отсутствия
одновременных вызовов. Системное разрешение DNS, TLS и присоединение потока
могут превысить `connectTimeout`; жёсткого общего срока завершения нет.

Самостоятельная демонстрация чтения и записи:

```sh
./build/bin/smart_home_mqtt_demo --host 127.0.0.1 --port 1883 --topic example/bytes --timeout 5
./build/bin/smart_home_mqtt_demo --host mqtt.example.org --topic example/bytes --ca-file ca.pem
```

Адрес и тема обязательны. `--ca-file` включает TLS, по умолчанию на порту 8883,
если `--port` не задан. Переменные `SMART_HOME_MQTT_USERNAME` и
`SMART_HOME_MQTT_PASSWORD` задают необязательные учётные данные. Демонстрация
подписывается, ожидает SUBACK, публикует бинарное сообщение, ожидает подтверждение
и читает ответ; тайм-аут или отказ дают код 1, неправильные параметры — код 2.
Успех даёт код 0. Для отключения сборки демонстрации:
`-DSMART_HOME_BUILD_MQTT_DEMO=OFF`.

`mqtt_tests` проверяет конфигурацию, ограничения очереди, ранние подтверждения,
отмену операций и жизненный цикл нескольких клиентов без брокера. На UNIX при
наличии исполняемого файла `mosquitto` дополнительно регистрируется
`mqtt_integration_tests`: тест запускает временные брокеры только на loopback,
проверяет QoS 0/1/2, бинарные и retained-сообщения, отписку, ограничения,
конкурентную публикацию, переподключение и отказ авторизации. Работающий
пользовательский брокер и интернет не требуются. Интеграционный тест имеет
лимит CTest 60 с; отключить его можно через
`-DSMART_HOME_MQTT_INTEGRATION_TESTS=OFF`.

## OpenWakeWord: ключевое слово «Нафаня»

`SmartHome::Oww` принимает последовательные кадры по 80 мс (1280 отсчётов
моно signed PCM16 при 16000 Гц) и возвращает вероятность ключевого слова `float`
в `[0, 1]`. Реализован полный ONNX-пайплайн OpenWakeWord: спектрограмма,
акустические признаки, бинарный классификатор. Python для работы модуля не нужен.

Для сборки нужен ONNX Runtime C++ SDK. CMake находит установленный пакет
`onnxruntime`; для отдельного SDK укажите
`-DSMART_HOME_ONNXRUNTIME_DIR=/path/to/onnxruntime` или `ONNXRUNTIME_ROOT`.
Публичный API и реализация модуля используют C++17, runtime скрыт за PIMPL.

Команда из корня проекта загружает [готовую модель «Нафаня»](https://github.com/fwartner/home-assistant-wakewords-collection/tree/main/ru/nafanya)
и две общие модели из [релиза OpenWakeWord v0.5.1](https://github.com/dscripka/openWakeWord/releases/tag/v0.5.1):

```sh
cmake -P oww/DownloadModels.cmake
```

Файлы сохраняются в `oww/models/`; можно задать `-DOWW_MODELS_DIR=/path/to/models`.
Доступна также отдельная цель `cmake --build build --target oww_models`.
Обычная сборка не скачивает модели. Загрузчик сохраняет существующие непустые
файлы и не устанавливает незавершённые загрузки. Источники закреплены и перечислены
в [oww/models/README.md](oww/models/README.md).

```cpp
#include <oww/OpenWakeWordDetector.h>

using namespace smart_home::oww;
OwwConfig config;
config.model_path = "oww/models/nafanya.onnx";
OpenWakeWordDetector detector(config);

PcmFrame frame{}; // Вызывающий код заполняет 1280 отсчётов очередных 80 мс.
const float probability = detector.processFrame(frame);
```

`melspec_model_path` и `embedding_model_path` в конфигурации позволяют хранить
общие модели отдельно; пустые пути означают файлы `melspectrogram.onnx` и
`embedding_model.onnx` рядом с классификатором. `getModelPath()` возвращает
исходный путь к классификатору. Все три файла проверяются и загружаются при
создании детектора. Частота отличается от 16000 Гц или число потоков меньше 1 —
`std::invalid_argument`; повреждённый ONNX или сбой инференса —
`std::runtime_error`. Несовместимые интерфейсы моделей также отклоняются.
Поддерживаются бинарные классификаторы float32 `[1, N, 96]` с фиксированным
`N` от 1 до 120 и одним выходным значением. Модель можно заменить без изменения
модуля, если она использует этот интерфейс OpenWakeWord.

Проверка длины кадра отключена по спецификации: указатель и перегрузка для
`std::vector<int16_t>` требуют доступности 1280 отсчётов; перегрузка для
`PcmFrame` задаёт размер типом. Контекст между кадрами сохраняется; один экземпляр
используется для одного потока аудио последовательно. При создании весь контекст
прогревается тишиной, буферы и тензоры переиспользуются. Число потоков инференса
по умолчанию равно 1; активное ожидание потоков отключено. Захват микрофона,
ресемплинг, порог срабатывания и обучение не входят в модуль.

`oww_tests` работает без сети на маленьких ONNX-графах, проверяя вычисления,
контекст, ошибки моделей и тысячи кадров. После загрузки комплекта можно
зарегистрировать отдельную проверку обученной модели:

```sh
cmake -B build -S . -DSMART_HOME_OWW_TEST_MODEL="$PWD/oww/models/nafanya.onnx"
cmake --build build -j
ctest --test-dir build -R oww --output-on-failure
```

Для общих моделей в другом каталоге задаются `SMART_HOME_OWW_TEST_MELSPEC` и
`SMART_HOME_OWW_TEST_EMBEDDING`. Smoke-тест обрабатывает 1000 кадров и проверяет
конечность/диапазон вероятностей, но не качество распознавания. Проверка на
записях слова «Нафаня» и замеры CPU/RAM на Raspberry Pi выполняются отдельно.
