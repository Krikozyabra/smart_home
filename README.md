## Снимки SQLite storage

`SQLiteDeviceStorage::dumpToFile(path)` синхронно сохраняет всю открытую
базу `main` в самостоятельный SQLite-файл, включая дополнительные таблицы,
локальные ID и состояние AUTOINCREMENT. Источник может находиться в RAM
или в файле. После dump работа продолжается с исходной базой.
Метод доступен через `IDeviceStorage`; реализация `InMemoryDeviceStorage`
сообщает `std::logic_error`, не создавая и не меняя файлы.

```cpp
smart_home::SQLiteDeviceStorage storage(":memory:", "data/inventory.sqlite");
storage.insert("physical-id", "driver-id", "Лампа");
smart_home::IDeviceStorage& inventory = storage;
inventory.dumpToFile("data/manual.sqlite"); // Явная ошибка передаётся вызывающему.
inventory.close(); // Финальный dump в data/inventory.sqlite и закрытие базы.
// Без явного close() деструктор выполняет последнюю попытку без исключений.
```

Родительский каталог должен существовать. Необязательный второй аргумент
конструктора задаёт путь финального dump; относительный путь фиксируется
при создании объекта. Без него автодампа нет. Явный dump не меняет этот
путь и не отменяет финальное сохранение. Ошибка финального dump однократно
сообщается через logging и не выходит исключением из деструктора.

`IDeviceStorage::close()` явно завершает работу: SQLite сохраняет настроенный
финальный dump, затем освобождает соединение; InMemoryDeviceStorage переходит
в закрытое состояние без записи файлов. После успеха повторный `close()` ничего
не делает, а остальные операции дают `std::logic_error`. Ошибка финального dump
при явном `close()` передаётся как `std::runtime_error` без логирования;
хранилище остаётся открытым, и после устранения причины можно повторить `close()`.
Деструктор после неудачного явного закрытия также пытается сохранить данные,
а после успешного `close()` повторного dump нет.

На Linux используется backup API SQLite, уникальный временный файл в
каталоге назначения, проверенное закрытие базы, `fsync` файла, атомарный
`rename` и `fsync` каталога. До rename ошибка оставляет прежний снимок
неизменным; ошибка после rename сообщает о неопределённости долговечности
замены. Ссылки, не обычные файлы и файловые псевдонимы рабочей базы
отклоняются. Вызывающий код сериализует обращения к источнику и обеспечивает
исключительный доступ к назначению без открытых соединений и внешних
WAL/journal-файлов. Фонового сохранения нет.

Контракт: [specs/storage/spec.md](specs/storage/spec.md).
Проверки: `ctest --test-dir build -R 'storage|sqlite_dump' --output-on-failure`.
Отдельный dump не заменяет публикацию полного поколения runtime.

## Драйверы устройств

`UniversalDeviceDriver` поддерживает восемь возможностей из
`CapabilityCatalog`. Регистрируйте функции создания по протоколу через
`DriverFactoryRegistry::add`. Консольное приложение использует
`createSimulatedDriver` для `simulated`.

Для Zigbee создайте `Zigbee2Mqtt` с вашим `mqtt::IMqttClient`,
зарегистрируйте `adapter.creator()` для `zigbee` и передавайте сообщения
подписки соответствующему драйверу через `adapter.applyTelemetry`.
Для сборки требуется `json-c` 0.15 или новее, например `libjson-c-dev`
в Debian. [Спецификация драйверов](specs/drivers/spec.md)

## Регистрация и восстановление устройств

`DeviceManager(storage, factories, devices, ontology)` получает зависимости по
ссылкам без владения. Приложение заранее создаёт каталог возможностей в ontology.
При регистрации менеджер добавляет обнаруженные возможности в драйвер
и связывает их с устройством через `HAS_FEATURE`. При холодном старте
возможности универсального драйвера восстанавливаются из этих связей.
Повторный вызов сохраняет ID, имя, драйвер с текущими значениями и назначенную
комнату. Несовпадение имени, лишние связи или отсутствие возможности в каталоге
вызывают ошибку; менеджер их автоматически не исправляет.

Все отсутствующие драйверы подготавливаются до изменения registry и графа.
После частичного отказа графа записи и драйверы сохраняются; повторный вызов
завершает недостающие изменения. Возвращаемое число восстановления учитывает
только добавленные драйверы. Менеджер не назначает комнаты, не сохраняет
состояние на диск и не закрывает ontology; это делает runtime.
Доступ сериализует вызывающий код.

Контракт, решения и выполненный план: [specs/device_management/](specs/device_management/).
Проверки: `ctest --test-dir build -R 'device_manager|discovery_service|logging_tests|runtime_' --output-on-failure`.

## Онтология дома (LadybugDB)

Для сборки нужен готовый C/C++ SDK LadybugDB с `include/lbug.hpp` и
`lib/liblbug.a` либо `lib/liblbug.so`. Путь задаётся явно, без зависимости от
расположения соседних проектов:

```sh
cmake -B build -S . -DSMART_HOME_LADYBUG_SDK_DIR=/path/to/ladybug-sdk
cmake --build build -j2
ctest --test-dir build --output-on-failure
cmake --build build --target docs
```

Вместо CMake-параметра можно задать `LADYBUG_SDK_DIR`. Для статического SDK
нужны OpenSSL и Threads. При настройке CMake компилирует, связывает и запускает
проверку выбранных заголовков и бинарной библиотеки. Проверены версии 0.21.2 и 0.22.3:
реализация требует C++20, а публичные заголовки и приложение остаются C++17.
Несовместимые SDK завершают настройку с диагностикой; автоматической загрузки нет.
Реализация файлового протокола рассчитана на Linux и локальную файловую систему
с `flock`, атомарным `rename` и `fsync`. Кросс-компиляция пока не поддерживается.

`SmartHome::Ontology` содержит узлы `rooms(id STRING, name STRING)`,
`devices(id INT64, name STRING)` и
`abilities(id STRING, name STRING, category STRING)` с первичными ключами `id`.
Связи направлены от устройств: `LOCATED_IN -> rooms`, `HAS_FEATURE -> abilities`.
Устройство может находиться только в одной комнате; переназначение выполняется
транзакционно. Повторное добавление возможности не создаёт вторую связь.
Методы `addRoom`, `addDevice`, `addAbility` создают либо обновляют свойства узла,
сохраняя его связи. Удаление узла удаляет его связи, но сохраняет соседние узлы.
Списки возвращаются в порядке ключей. Значения передаются параметрами Cypher.

У устройства нет статического поля типа: его функции определяют связи
`HAS_FEATURE`, а `getDevicesWithAbility()` выбирает устройства по возможности.
Старые базы с `devices.type` отклоняются с требованием явной миграции;
автоматического изменения или пересоздания схемы нет.
Runtime использует контракт без поля типа. Консольные категории `light` и
`temperature_sensor` определяются по inventory в runtime и не хранятся в графе.

Ключ устройства совпадает с локальным `DeviceId`; ключ возможности совпадает с
`CapabilityDescriptor::getId()` (`on_off`, `brightness`, `color`, `temperature`).
SQLite / `IDeviceStorage` по-прежнему владеют физическими идентификаторами,
метаданными обнаружения и привязками драйверов. Онтология хранит семантические
узлы и связи, не копирует аппаратные адреса и не выполняет операции с драйверами.
Общей транзакции с SQLite нет: вызывающая сторона сначала сохраняет инвентарь,
затем повторяемо обновляет онтологию и обрабатывает возможный частичный сбой.
Основной `smart_home` запускает консольный runtime: обнаруживает две лампы
и датчик, выполняет адресные и групповые команды и восстанавливает полное
состояние. Пользовательские размещения устройств сохраняются при перезапуске.
Описание: [specs/runtime/spec.md](specs/runtime/spec.md).

```sh
./build/bin/smart_home --runtime-state-dir=data/runtime --log-level=info
```

| CLI (также допускается `--имя=значение`) | Переменная окружения | По умолчанию |
| --- | --- | --- |
| `--runtime-state-dir` | `SMART_HOME_RUNTIME_STATE_DIR` | `data/runtime` |
| `--runtime-ram-dir` | `SMART_HOME_RUNTIME_RAM_DIR` | `/dev/shm` |
| `--runtime-snapshot-capacity` | `SMART_HOME_RUNTIME_SNAPSHOT_CAPACITY` | `4` |

Команды: `help`, `list`, `show <id>`, `scan`, `save`, `exit`,
`<id> <operation> [arguments]`, `<room> <type> <operation> [arguments]`.
Например: `1 brightness.set 75` или `living_room light on_off.set true`.
Результат команды и подтверждение сохранения выводятся отдельно.
`exit`, EOF, SIGINT/SIGTERM завершают работу с финальным сохранением.

Runtime работает только в RAM (tmpfs/ramfs), без disk fallback; постоянный
каталог содержит целые поколения SQLite, онтологии и значений возможностей.
После изменения worker публикует поколение через `CURRENT`.
Периодическое сохранение отключено. Ёмкость очереди учитывает также
выполняемый снимок и ещё не полученные результаты. При заполнении изменение
отклоняется до выполнения.
При ошибке сохранения изменения остаются в RAM; `save` повторяет попытку.
Повреждение зафиксированного поколения вызывает ошибку запуска.

`SmartHome::Persistence` хранит типизированные значения в `device_properties`
вместе с ревизией в `runtime_meta`. Рабочие снимки SQLite и LadybugDB
передаются воркеру в RAM. Воркер вычисляет SHA-256 при копировании и
подтверждает сохранение после атомарной замены `CURRENT` и `fsync` каталога.
Ранее сохранённые поколения v1 с `runtime_values` читаются и при следующем
сохранении переходят на `device_properties`. [Контракт и проверки](specs/persistence/spec.md).

CLI переопределяет окружение. Некорректная конфигурация даёт код 2.
Самостоятельные `--ontology-*` и `SMART_HOME_ONTOLOGY_*` в runtime
отклоняются: назначение файлов, период и RAM-каталог задаёт композиция.
Автоматической миграции прежней демонстрационной базы нет.

Ниже описан протокол **самостоятельной библиотеки ontology**. В runtime
её постоянный файл является промежуточным checkpoint в RAM;
долговечность общего состояния обеспечивает публикация поколения.

На старте основной файл копируется в приватный каталог с правами 0700 внутри
`/dev/shm`. Движок использует только рабочую копию. Буферный пул по умолчанию —
64 МиБ, число потоков — 2; эти лимиты задаются через `OntologyConfig`.
Перед созданием каталога проверяется запас свободного места (минимум 64 МиБ,
для существующей базы — минимум три размера файла). Это предварительная
проверка, а не резервирование: последующее заполнение tmpfs может вызвать ошибку.
При недоступной RAM запуск завершается с ошибкой. Только явное разрешение
`allow_disk_fallback` / значение `1` допускает временный рабочий каталог рядом
с постоянным файлом; при этом выдаётся предупреждение.

`OntologyConfig::database_path` задаёт исходную базу для загрузки, а `dump_path`
задаёт финальный автодамп. По умолчанию `database_path` —
`data/home_ontology.lbdb`, `dump_path` пуст: закрытие не сохраняет изменения.
`configFromEnvironment()` читает `SMART_HOME_ONTOLOGY_PATH` сразу в оба поля,
а также `SMART_HOME_ONTOLOGY_RAM_DIR` и `SMART_HOME_ONTOLOGY_ALLOW_DISK_FALLBACK`.
Переменная прежнего таймера больше не используется; фонового сохранения нет.
Относительные пути конфигурации фиксируются при создании экземпляра.

```cpp
smart_home::ontology::OntologyConfig config;
config.database_path = "data/home_ontology.lbdb";
config.dump_path = config.database_path; // Явно включить финальное сохранение.
smart_home::ontology::LadybugOntologyStorage graph(config);
graph.addRoom({"living_room", "Гостиная"});
graph.dumpToFile("data/manual.lbdb"); // Родитель существует; работа продолжается в RAM.
graph.close(); // Финальный dump в config.dump_path, затем освобождение ресурсов.
```

Исходная база копируется в RAM только на старте. Обычные запросы не изменяют
исходный файл. Новая схема сразу сохраняется только при заданном `dump_path`.
`dumpToFile(path)` блокирует запросы, выполняет `CHECKPOINT`, закрывает движок,
копирует файл во временный файл рядом с назначением, выполняет `fsync`, атомарное
переименование и `fsync` каталога, затем открывает RAM-базу снова. Каждый вызов
создаёт снимок, даже без новых изменений; явный dump не меняет `dump_path`.
Протокол основан на [транзакциях и CHECKPOINT Ladybug](https://docs.ladybugdb.com/cypher/transaction/)
и [описании файлов базы](https://docs.ladybugdb.com/developer-guide/files/).

Родитель назначения dump должен существовать. Пустые пути, NUL, симлинки,
каталоги, жёсткие ссылки, файлы внутри рабочего каталога и активный lockfile
отклоняются. Вызывающий обеспечивает исключительный доступ к назначению без
открытого движка и внешних WAL/sidecar-файлов.

Блокировка отдельного `.lock` удерживается весь срок жизни экземпляра; этот файл
не удаляется, его наличие после остановки нормально. Канонизация путей учитывает
символические ссылки, жёсткие ссылки на базу запрещены. Все писатели должны
соблюдать эту блокировку: параллельно открывать постоянную базу сторонним клиентом
нельзя. WAL/теневые файлы постоянной базы восстанавливаются самим движком до
копирования. Повреждённые базы, несовместимая схема и ошибки воспроизведения WAL
не приводят к автоматическому созданию пустой базы.

При ошибке до переименования предыдущий снимок сохраняется. Ошибка после
переименования означает неопределённость долговечности замены; требуется
повторный `dumpToFile(path)`. Ошибка явного `close()` передаётся вызывающему
коду; после исправления причины можно повторить закрытие. Деструктор выполняет
последнюю попытку без исключений, при неудаче логирует Critical и сохраняет
рабочие файлы для ручного восстановления. Неудачное повторное открытие движка
запрещает запросы и dump; `close()` может сохранить оставшуюся рабочую копию.
После успешного закрытия повторный `close()` безопасен, остальные операции
сообщают `std::logic_error`.

При аварийном завершении теряются изменения после последнего успешного снимка.
Оставшиеся RAM-каталоги не восстанавливаются автоматически. Проверив завершение
процесса, администратор может сохранить или удалить их вручную. Остатки собственных
временных файлов снимка исходной базы удаляются при старте под блокировкой.

Наборы CTest: `ontology_config_tests`, `ontology_storage_tests`,
`ontology_dump_tests`, `ontology_concurrency_tests`. Они используют реальный SDK,
изолированные каталоги и управляемые точки отказа. Проверяются связи, параметры,
произвольные назначения dump, жизненный цикл с автодампом и без, атомарность,
восстановление WAL, межпроцессная блокировка и конкурентные запросы/dump/close.
Дополнительная проверка `/dev/shm` внутри набора конфигурации явно пропускается,
если среда запрещает запись туда; остальные проверки выполняются в изолированной
настраиваемой рабочей директории. Глобальные настройки/данные приложения не используются.

## Диагностическое логирование

Для сборки требуется пакет разработки spdlog (`find_package(spdlog CONFIG)`).
Если пакет не установлен, включите загрузку закрепленной версии v1.17.0:
`cmake -B build -S . -DSMART_HOME_FETCH_SPDLOG=ON` (требуется доступ к GitHub и Git).

Логирование синхронное и потокобезопасное. Диагностика выводится в stderr и
`logs/smart_home.log`, относительно текущего рабочего каталога. Измерения остаются
в stdout. Порог по умолчанию — INFO; файл ротируется при 5 МиБ, сохраняются три
архивных файла плюс текущий. Отдельная запись больше порога может превысить его.

```sh
./build/bin/smart_home --log-level=debug --log-file=logs/smart_home.log
./build/bin/smart_home --log-level=off --log-file=
```

| CLI | Переменная окружения | Значение по умолчанию |
| --- | --- | --- |
| `--log-level` | `SMART_HOME_LOG_LEVEL` | `info` |
| `--log-file` | `SMART_HOME_LOG_FILE` | `logs/smart_home.log` |
| `--log-max-size-mib` | `SMART_HOME_LOG_MAX_SIZE_MIB` | `5` |
| `--log-max-files` | `SMART_HOME_LOG_MAX_FILES` | `3` |

Приоритет для каждого поля: CLI > окружение > значения по умолчанию. Поддерживаются
формы `--ключ=значение` и `--ключ значение`; при повторении действует последнее
значение. Пустой путь отключает файловый вывод. Размер должен быть положительным,
число архивов — от 1 до 200000. Неизвестные аргументы и некорректные значения CLI
дают код выхода 2 до выполнения команд. Некорректное окружение вызывает
предупреждение и заменяется значением по умолчанию.

Уровни, без учета регистра: TRACE (трассировка), DEBUG (отладка), INFO (жизненный
цикл), WARN (обработанное отклонение), ERROR (ошибка операции с продолжением),
CRITICAL (фатальное завершение), OFF (отключение обычных записей). DEBUG и TRACE
доступны и в Release. Ошибка записывается один раз в месте обработки; физические
адреса и произвольный текст исключений в диагностику не копируются.

При невозможности открыть файл сохраняется вывод в stderr. Ошибки приемников
вызывают прямое предупреждение в stderr, не чаще одного раза за пять секунд,
и не меняют исключения бизнес-логики. Служебные сообщения об ошибках самого
логирования могут выводиться при OFF. До инициализации и после завершения WARN
и выше выводятся минимальным обработчиком в stderr. Инициализацией и завершением
владеет `main`; библиотеки не меняют глобальный реестр spdlog.

## MQTT-клиент

Модуль `SmartHome::Mqtt` использует C++ библиотеку Mosquitto (`libmosquittopp`) и
поддерживает MQTT 3.1.1. Для сборки нужны `pkg-config` и пакеты разработки
`libmosquittopp` и `libmosquitto` версии 2.0 или новее. На Arch/Manjaro они входят
в `mosquitto`; на Debian/Ubuntu установите `libmosquittopp-dev libmosquitto-dev`.
Библиотека находится через pkg-config; для отдельной установки задайте
`PKG_CONFIG_PATH`. Загрузка исходников при конфигурации не выполняется.

Публичный интерфейс — `mqtt/interfaces/IMqttClient.h`, реализация —
`mqtt/MosquittoClient.h`. В публичных заголовках нет типов Mosquitto.
Клиент отправляет бинарные сообщения через `publish`, принимает их после
`subscribe` через неблокирующий `tryRead` или `readFor` с тайм-аутом.
Тема и данные входящего `MqttMessage` принадлежат сообщению; нулевые байты и
пустая полезная нагрузка допустимы. Темы, форматы данных и тип брокера задаёт
вызывающий код. Связь с драйверами и диспетчером команд пока не задаётся.

```cpp
#include "mqtt/MosquittoClient.h"
#include <chrono>

using namespace smart_home::mqtt;
using namespace std::chrono_literals;

MqttConfig config;
config.host = "127.0.0.1"; // Замените адресом своего брокера.
config.port = 1883;
MosquittoClient client;
client.connect(config); // Ожидает успешный CONNACK.
auto subscription = client.subscribe("example/bytes", MqttQoS::AtLeastOnce);
if (client.waitForOperation(subscription, 2s).status != MqttOperationStatus::Completed)
    throw MqttException("Subscription failed or timed out.");
auto publication = client.publish("example/bytes", {0, 1, 255}, MqttQoS::AtLeastOnce);
if (!client.waitForDelivery(publication, 2s))
    throw MqttException("Publish failed or timed out.");
MqttMessage message;
if (client.readFor(2s, message)) {
    // Используйте message.topic и message.payload в потоке приложения.
}
client.disconnect();
```

`publish`, `subscribe` и `unsubscribe` возвращают собственный токен операции.
Возврат означает принятие запроса библиотекой. `waitForOperation` различает
`Pending`, `Completed`, `Rejected`, `Cancelled` и `Unknown`; для SUBACK возвращает
разрешённый QoS. Терминальный результат читается один раз и освобождает место
для следующей операции. После тайм-аута `Pending` токен остаётся действительным:
ожидание можно повторить. `waitForDelivery` — сокращённая проверка `Completed`.
Для QoS 0 это отправка, для QoS 1 — PUBACK, для QoS 2 — PUBCOMP; подтверждение
не означает выполнение команды другим приложением. MQTT 3.1.1 не предоставляет
отрицательный PUBACK для проверки прав публикации.

`MqttConfig` задаёт обязательный host, порт, clientId, cleanSession, keepalive,
тайм-аут CONNACK, задержки переподключения и лимиты ресурсов. По умолчанию:

| Параметр | Значение |
| --- | --- |
| Порт / keepalive / cleanSession | 1883 / 60 с / true |
| connectTimeout | 5 с ожидания CONNACK |
| reconnectDelayInitial / reconnectDelayMax | 1 с / 30 с, экспоненциальный рост |
| receiveQueueCapacity / receiveQueueBytes | 1000 сообщений / 16 МиБ темы и данных |
| maxPayloadBytes / maxPendingPublishBytes | 16 МиБ / 16 МиБ до подтверждений |
| maxPendingOperations | 256 токенов, включая непрочитанные результаты |
| maxSubscriptions | 128 фильтров, включая сохранённые намерения отписки |

При переполнении входящей очереди отбрасывается новое сообщение; уже принятые
сохраняют FIFO. `droppedMessages()` показывает потери после последнего `connect`.
Предупреждение ограничено одним сообщением за пять секунд. При превышении лимита
исходящих операций выбрасывается `MqttException`. Обязательно читайте результаты
всех своих токенов, включая подписки и отписки. Сетевые callback не вызывают
пользовательский код и не выводят адреса, темы, пароли или содержимое сообщений.

При потере соединения состояние становится `Connecting`; после переподключения
повторяются подписки и намерения отписки, а библиотека может повторить публикации
QoS 1/2. Запросы при отсутствии соединения отклоняются. Отказ CONNACK, ошибка
авторизации, TLS или протокола прекращают автоматические попытки. После неудачного
первоначального подключения клиент очищает транспорт; `connect` можно повторить.
Для запущенного клиента сначала вызовите `disconnect`.

Пароль задаётся через `config.username` и `config.password`. TLS включается
через `config.tls`: необходим `caFile`, а для взаимной авторизации —
`clientCertFile` и `clientKeyFile` без парольного шифрования. По умолчанию
`verifyPeer=true` проверяет сертификат и имя брокера. Порт библиотеки задаётся
явно, например 8883; включение TLS в конфигурации не переписывает порт.
Для постоянной сессии `cleanSession=false` требуется непустой `clientId`.

Методы потокобезопасны; операции управления соединением сериализованы.
`disconnect` будит ожидающих читателей, отменяет неподтверждённые операции и
присоединяет сетевой поток до уничтожения транспорта. Оставшиеся сообщения
можно дочитать; следующий `connect` очищает очередь и старые токены.
Глобальная библиотека инициализируется до создания транспорта и освобождается
после уничтожения последнего клиента. Перед уничтожением клиента завершите
свои потоки, обращающиеся к нему; перемещение также требует отсутствия
одновременных вызовов. Системное разрешение DNS, TLS и присоединение потока
могут превысить `connectTimeout`; жёсткого общего срока завершения нет.

Самостоятельная демонстрация чтения и записи:

```sh
./build/bin/smart_home_mqtt_demo --host 127.0.0.1 --port 1883 --topic example/bytes --timeout 5
./build/bin/smart_home_mqtt_demo --host mqtt.example.org --topic example/bytes --ca-file ca.pem
```

Адрес и тема обязательны. `--ca-file` включает TLS, по умолчанию на порту 8883,
если `--port` не задан. Переменные `SMART_HOME_MQTT_USERNAME` и
`SMART_HOME_MQTT_PASSWORD` задают необязательные учётные данные. Демонстрация
подписывается, ожидает SUBACK, публикует бинарное сообщение, ожидает подтверждение
и читает ответ; тайм-аут или отказ дают код 1, неправильные параметры — код 2.
Успех даёт код 0. Для отключения сборки демонстрации:
`-DSMART_HOME_BUILD_MQTT_DEMO=OFF`.

`mqtt_tests` проверяет конфигурацию, ограничения очереди, ранние подтверждения,
отмену операций и жизненный цикл нескольких клиентов без брокера. На UNIX при
наличии исполняемого файла `mosquitto` дополнительно регистрируется
`mqtt_integration_tests`: тест запускает временные брокеры только на loopback,
проверяет QoS 0/1/2, бинарные и retained-сообщения, отписку, ограничения,
конкурентную публикацию, переподключение и отказ авторизации. Работающий
пользовательский брокер и интернет не требуются. Интеграционный тест имеет
лимит CTest 60 с; отключить его можно через
`-DSMART_HOME_MQTT_INTEGRATION_TESTS=OFF`.

## OpenWakeWord: ключевое слово «Нафаня»

`SmartHome::Oww` принимает последовательные кадры по 80 мс (1280 отсчётов
моно signed PCM16 при 16000 Гц) и возвращает вероятность ключевого слова `float`
в `[0, 1]`. Реализован полный ONNX-пайплайн OpenWakeWord: спектрограмма,
акустические признаки, бинарный классификатор. Python для работы модуля не нужен.

Для сборки нужен ONNX Runtime C++ SDK. CMake находит установленный пакет
`onnxruntime`; для отдельного SDK укажите
`-DSMART_HOME_ONNXRUNTIME_DIR=/path/to/onnxruntime` или `ONNXRUNTIME_ROOT`.
Публичный API и реализация модуля используют C++17, runtime скрыт за PIMPL.

Команда из корня проекта загружает [готовую модель «Нафаня»](https://github.com/fwartner/home-assistant-wakewords-collection/tree/main/ru/nafanya)
и две общие модели из [релиза OpenWakeWord v0.5.1](https://github.com/dscripka/openWakeWord/releases/tag/v0.5.1):

```sh
cmake -P oww/DownloadModels.cmake
```

Файлы сохраняются в `oww/models/`; можно задать `-DOWW_MODELS_DIR=/path/to/models`.
Доступна также отдельная цель `cmake --build build --target oww_models`.
Обычная сборка не скачивает модели. Загрузчик сохраняет существующие непустые
файлы и не устанавливает незавершённые загрузки. Источники закреплены и перечислены
в [oww/models/README.md](oww/models/README.md).

```cpp
#include <oww/OpenWakeWordDetector.h>

using namespace smart_home::oww;
OwwConfig config;
config.model_path = "oww/models/nafanya.onnx";
OpenWakeWordDetector detector(config);

PcmFrame frame{}; // Вызывающий код заполняет 1280 отсчётов очередных 80 мс.
const float probability = detector.processFrame(frame);
```

`melspec_model_path` и `embedding_model_path` в конфигурации позволяют хранить
общие модели отдельно; пустые пути означают файлы `melspectrogram.onnx` и
`embedding_model.onnx` рядом с классификатором. `getModelPath()` возвращает
исходный путь к классификатору. Все три файла проверяются и загружаются при
создании детектора. Частота отличается от 16000 Гц или число потоков меньше 1 —
`std::invalid_argument`; повреждённый ONNX или сбой инференса —
`std::runtime_error`. Несовместимые интерфейсы моделей также отклоняются.
Поддерживаются бинарные классификаторы float32 `[1, N, 96]` с фиксированным
`N` от 1 до 120 и одним выходным значением. Модель можно заменить без изменения
модуля, если она использует этот интерфейс OpenWakeWord.

Проверка длины кадра отключена по спецификации: указатель и перегрузка для
`std::vector<int16_t>` требуют доступности 1280 отсчётов; перегрузка для
`PcmFrame` задаёт размер типом. Контекст между кадрами сохраняется; один экземпляр
используется для одного потока аудио последовательно. При создании весь контекст
прогревается тишиной, буферы и тензоры переиспользуются. Число потоков инференса
по умолчанию равно 1; активное ожидание потоков отключено. Захват микрофона,
ресемплинг, порог срабатывания и обучение не входят в модуль.

`oww_tests` работает без сети на маленьких ONNX-графах, проверяя вычисления,
контекст, ошибки моделей и тысячи кадров. После загрузки комплекта можно
зарегистрировать отдельную проверку обученной модели:

```sh
cmake -B build -S . -DSMART_HOME_OWW_TEST_MODEL="$PWD/oww/models/nafanya.onnx"
cmake --build build -j
ctest --test-dir build -R oww --output-on-failure
```

Для общих моделей в другом каталоге задаются `SMART_HOME_OWW_TEST_MELSPEC` и
`SMART_HOME_OWW_TEST_EMBEDDING`. Smoke-тест обрабатывает 1000 кадров и проверяет
конечность/диапазон вероятностей, но не качество распознавания. Проверка на
записях слова «Нафаня» и замеры CPU/RAM на Raspberry Pi выполняются отдельно.

## Захват звука (audio)

`SmartHome::Audio` требует Linux и ALSA development package (`libasound2-dev`
в Debian/Raspberry Pi OS). Публичные заголовки C++17 не раскрывают ALSA;
библиотеки ALSA, Threads и Logging подключаются приватно. Приложение не начинает
захват автоматически. Параметры и контракты: [specs/audio/spec.md](specs/audio/spec.md).

```cpp
#include <audio/AlsaAudioCapture.h>
#include <chrono>

smart_home::audio::AudioConfig config;
config.device_name = "default"; // Например, "hw:1,0" для конкретного устройства.
smart_home::audio::AlsaAudioCapture microphone(config);
auto pcm = microphone.recordFor(std::chrono::milliseconds(1000));
// 16000 signed PCM16 отсчётов; в стерео — interleaved L, R.
microphone.startContinuous();
// snapshot() можно вызывать из нескольких потоков, пока приложение работает.
auto snapshot = microphone.snapshot();
microphone.stopContinuous(); // Пробуждает poll, присоединяет worker, повторяет ошибку.
```

По умолчанию используются 16000 Гц, Mono, кадр 80 мс (1280 отсчётов),
кольцо 125 кадров (10 секунд, 320000 байт PCM). Настройки доступны через
`getConfig()`. Частота и формат устанавливаются точно; преобразования возможны
в выбранном ALSA plugin, собственного ресемплера нет. Длительность обязана
давать целое число отсчётов на канал. Параметры и переполнения проверяются
до выделения памяти; нехватка памяти передаётся как `bad_alloc`.

Снимок содержит собственные копии полных кадров от старого к новому;
чтение их не удаляет. При заполнении кольца перезаписывается старейший кадр.
`sequence` начинается с нуля, `session_id` меняется при новом запуске.
Повторный запуск во время записи не очищает кольцо; остановка повторяема.
Разовая запись не меняет кольцо и отклоняется при занятом режиме (`logic_error`).
Конкурирующие управляющие вызовы во время разовой записи также отклоняются.
Новый запуск после штатной остановки очищает кольцо. Незавершённые кадры
при остановке/ошибке отбрасываются, старые полные кадры остаются доступны.

Ошибки открытия/формата, overrun, suspend и отключение дают `runtime_error`;
потери не маскируются тишиной и не восстанавливаются автоматически.
Без прогресса запись прекращается через 5 секунд. Остановка имеет отдельный
дескриптор пробуждения и не ждёт этого тайм-аута. Целевые 250 мс задержки
остановки требуют измерения на Raspberry Pi; на загруженной ОС срок не гарантирован.
Ошибку worker можно получить через `rethrowIfFailed()` или `stopContinuous()`;
повторное чтение её не очищает. После ошибки нужен новый экземпляр.
Логируйте ошибку один раз на границе её обработки. Деструктор присоединяет
поток без исключений и сообщает об оставленной без чтения ошибке; внешние
потоки должны завершить обращения к объекту до его уничтожения.

Для передачи в oww сначала проверьте настройки, затем обрабатывайте снимки
последовательно одним потребителем. Ниже тело обработчика очередного снимка;
`wake_config` содержит пути моделей, а `on_probability` — обработчик результата:

```cpp
#include <oww/OpenWakeWordDetector.h>
#include <memory>
#include <optional>
#include <stdexcept>

const auto format = microphone.getConfig();
if (format.sample_rate_hz != 16000 ||
    format.channels != smart_home::audio::Channels::Mono ||
    format.frame_duration != std::chrono::milliseconds(80))
    throw std::invalid_argument("audio format is incompatible with OWW");

std::unique_ptr<smart_home::oww::OpenWakeWordDetector> detector;
std::uint64_t session = 0;
std::optional<std::uint64_t> last_sequence;
auto consume = [&](const smart_home::audio::AudioSnapshot &copy) {
    if (copy.session_id != session) {
        session = copy.session_id;
        last_sequence.reset();
        detector.reset();
    }
    for (const auto &frame : copy.frames) {
        if (last_sequence && frame.sequence <= *last_sequence) continue;
        if (frame.samples.size() != smart_home::oww::FrameSamples)
            throw std::runtime_error("incomplete OWW frame");
        if (!detector || (last_sequence && frame.sequence != *last_sequence + 1))
            detector = std::make_unique<smart_home::oww::OpenWakeWordDetector>(wake_config);
        on_probability(detector->processFrame(frame.samples));
        last_sequence = frame.sequence;
    }
};
// Периодически: microphone.rethrowIfFailed(); consume(microphone.snapshot());
// Обработка идёт вне блокировки кольца; смена сеанса/пропуск сбрасывает контекст.
```

Четыре набора `audio_*_tests` работают без микрофона и сети: проверяют размеры,
PCM, короткие чтения и errno, тайм-аут, кольцо, ошибки и конкурентный lifecycle.
Аппаратный тест регистрируется только с явно указанным PCM:

```sh
cmake -S . -B build -DSMART_HOME_AUDIO_TEST_DEVICE=plughw:1,0
cmake --build build -j 4
ctest --test-dir build -R audio --output-on-failure
```

Тест запрашивает 16000 Гц / Mono / PCM16. `hw:1,0` обращается к аппаратуре
напрямую: если она не поддерживает один канал, настройка завершится ошибкой
`channels=1: Invalid argument`; аналогично отклоняется неподдерживаемая частота.
`plughw:1,0` явно разрешает преобразования каналов, частоты и формата средствами
ALSA, сохраняя запрошенный формат на входе audio. Карта и устройство `1,0`
в примере должны соответствовать вашему микрофону (`arecord -l`).
См. [описание ALSA hw и plug](https://www.alsa-project.org/alsa-doc/alsa-lib/pcm_plugins.html).
Модуль не заменяет `hw` на `plughw` автоматически. Отказ других форматов,
качество звука, CPU/RAM, длительный захват и задержка остановки на Raspberry Pi
проверяются отдельно. Успех без аппаратного теста не подтверждает эти свойства.

### Консольная проверка микрофона и OpenWakeWord

Один исполняемый файл `smart_home_audio_oww_demo` поддерживает оба режима:
живой захват с детекцией и отдельную запись пяти секунд с последующим анализом.
Соберите его и укажите модель ключевого слова и PCM вашего микрофона:

```sh
cmake -S . -B build -DSMART_HOME_BUILD_AUDIO_OWW_DEMO=ON
cmake --build build --target smart_home_audio_oww_demo -j 4
./build/bin/smart_home_audio_oww_demo \
  --device plughw:1,0 --model oww/models/nafanya.onnx --threshold 0.5
```

Комплект моделей должен уже существовать. При необходимости явно выполните
`cmake --build build --target oww_models` для загрузки; сам demo ничего
не скачивает. По умолчанию `melspectrogram.onnx` и `embedding_model.onnx`
ищутся рядом с классификатором. Другие пути задаются `--melspec FILE`
и `--embedding FILE`. Без `--device` используется ALSA `default`.

Введите команду и нажмите Enter:

| Команда | Действие |
|---|---|
| `start` | Начать запись и непрерывную детекцию |
| `stop` | Остановить микрофон, обработать остаток кольца, показать итог |
| `sample` | Записать 5 секунд, затем выполнить детекцию и показать итог |
| `help` | Показать команды |
| `quit` | Остановить запись и выйти; EOF также завершает программу |

При `sample` сначала остановите live командой `stop`. Говорить нужно после
сообщения `Recording 5 seconds; speak now...`. Образец хранится только в RAM.
Последние 640 отсчётов дополняются тишиной до полного кадра OWW: обрабатываются
63 кадра. Каждая запись получает свежий контекст детектора.

Консоль показывает вероятности примерно раз в секунду и `WAKE WORD detected`
при переходе через порог, а в итоге — количество кадров, пиковую вероятность
и число срабатываний. Порог настраивается в диапазоне `(0, 1]`; он требует
подбора под модель и микрофон. При пропуске кадров выводится предупреждение,
контекст детектора сбрасывается. Ошибки устройства или инференса завершают
программу с сообщением. Программный тест проверяет связь модулей без микрофона,
но не качество распознавания:

```sh
ctest --test-dir build -R audio_oww_demo --output-on-failure
```

Интеграционный тест регистрируется при наличии Python 3. Само приложение
написано на C++17 и не требует Python для запуска.

Спецификация сценария: [specs/audio/console-demo.md](specs/audio/console-demo.md).
