# Работа над проектом

## Особенности проекта
- Проект разрабатывается под Raspberry Pi 4b 8/120 (SD-card)
- Проект является информационной системой для управления умным домом с адаптацией к пользователю

## Архитектура проекта

Проект — модульное C++-приложение с CMake (минимум 3.20). Публичные
интерфейсы ориентированы на C++17. Модули собираются в статические библиотеки
с alias `SmartHome::<Module>`; `common` — INTERFACE-библиотека.
Точка сборки объектов и управления жизненным циклом приложения — `src/`.
Сервисы получают зависимости явно через конструкторы; не заменяй это
глобальным поиском сервисов.

### Карта модулей

| Каталог | Ответственность |
|---|---|
| `common` | Общие типы, в том числе локальный `DeviceId` |
| `devices` | Объекты устройств и узкие интерфейсы возможностей: включение, яркость, цвет, температура |
| `descriptors` | Описание устройств, возможностей, операций и параметров |
| `drivers` | Драйверы связывают объект устройства с дескриптором; фабрики создают драйверы |
| `registry` | Владение активными драйверами по `DeviceId` и фабриками по `driver_id` |
| `command` | Команда и типизированное значение её аргументов/результата |
| `execution` | `CommandDispatcher`: поиск устройства, проверка операции и аргументов, вызов обработчика |
| `storage` | `IDeviceStorage`, реализации в памяти и SQLite; инвентарь, физические идентификаторы и привязки драйверов |
| `device_management` | `DeviceManager`: восстановление сохранённых и регистрация обнаруженных устройств через storage, фабрики и registry |
| `discovery` | Источники обнаружения и `DiscoveryService`; результаты и обработанные ошибки в `DiscoveryReport` |
| `ontology` | Семантический граф комнат, устройств и возможностей, связи и сохранение через LadybugDB |
| `oww` | Потоковый ONNX-пайплайн OpenWakeWord: PCM-кадр → вероятность ключевого слова |
| `mqtt` | MQTT-транспорт через Mosquitto: соединение, сообщения, подписки и отслеживание операций |
| `audio` | ALSA-захват PCM16: разовая запись и потоковое кольцо со снимками |
| `logging` | Общий фасад диагностики; spdlog скрыт от потребителей |
| `cli` | Разбор командных строк, проверка аргументов, реестр команд и форматирование ответов |
| `src` | Исполняемые файлы, конфигурация запуска и композиция компонентов |
| `tests` | Самостоятельные тестовые программы, `TestUtil.h` и регистрация в CTest |
| `cmake` | Настройка внешних SDK, зависимостей и Doxygen |
| `specs` | Спецификации, планы и технические решения по функциям |

Контракты audio описаны в `specs/audio/`. Захват запускается явно;
готового голосового сценария и автоматической связи с oww нет.

Основные потоки взаимодействия:

- Обнаружение: источник → `DiscoveryService` → `DeviceManager` →
  хранилище и фабрика → `DeviceRegistry`.
- Выполнение: `Command` → `CommandDispatcher` → дескриптор операции →
  интерфейс возможности объекта устройства, полученного через драйвер.
- Онтология связывает семантические записи с инвентарём по локальному
  `DeviceId`. Физические адреса и привязки драйверов остаются в storage.
  Общей транзакции SQLite и LadybugDB нет; частичный сбой обрабатывает
  вызывающий код.
- MQTT и OWW предоставляют отдельные инфраструктурные API. Само наличие
  модулей не означает автоматической маршрутизации сообщений в команды
  или готового голосового сценария.

## Архитектура нового модуля

Основные примеры — `oww` и `ontology`. Используй их разделение контракта,
конфигурации и реализации, учитывая различия в потоковой модели.

```text
module/
  CMakeLists.txt
  include/module/
    IModule.h          # контракт, если нужна подмена реализации
    ModuleConfig.h     # настройки и validateConfig
    ConcreteModule.h   # публичная реализация без типов внешнего SDK
  src/
    ModuleConfig.cpp
    ConcreteModule.cpp
    Testing.h          # при необходимости: приватные точки доступа тестов
```

- Контракт и данные находятся в `include/<module>/`, детали — в `src/`.
  Приватные заголовки не включаются публичными потребителями.
- Для автономных новых модулей используй `smart_home::<module>`;
  существующее ядро использует `smart_home`. Не переноси старые типы
  между пространствами имён без отдельной причины.
- Настройки — отдельная структура с явными значениями по умолчанию,
  единицами измерения и проверкой `validateConfig()`. Отделяй проверку
  параметров от открытия ресурсов. Чтение окружения, если нужно,
  оформляй отдельной функцией, как в ontology.
- Публичный API документируй на русском через Doxygen: владение,
  предусловия, размеры, ошибки, потокобезопасность и срок жизни ссылок.
- Зависимости задавай через CMake targets. `PUBLIC` нужен для требований
  публичного API; внешний SDK и logging оставляй `PRIVATE`, если их типы
  не выходят в заголовки. Существующие CMake-файлы местами устроены иначе;
  не исправляй их попутно.
- Внешний SDK может требовать более нового стандарта внутри реализации:
  ontology использует настраиваемый стандарт SDK, сохраняя публичный C++17.
  Не распространяй это требование автоматически на приложение.

## Паттерны и примеры

### Интерфейс, адаптер и PIMPL

`IOpenWakeWord` / `OpenWakeWordDetector` и `IOntologyStorage` /
`LadybugOntologyStorage` отделяют контракт от конкретного SDK.
Реализации скрывают SDK, ресурсы и внутреннее состояние в `Impl`, которым
владеет `std::unique_ptr`. Деструктор класса с неполным `Impl` определяется
в `.cpp`. Используй этот подход для ресурсоёмких интеграций, а не добавляй
виртуальный интерфейс и PIMPL каждому простому типу данных.

### RAII и явное владение

Файлы, блокировки, соединения, сессии SDK и потоки должны иметь владельца.
Ресурсы освобождаются и при частичной неудаче конструктора. Контекстные
объекты OWW и ontology не копируются. Реестры владеют драйверами и фабриками
через `unique_ptr`; возвращаемые указатели и переданные сервисам ссылки
не передают владение. Не вводи `shared_ptr` без совместного владения.

Для операций завершения, способных завершиться ошибкой, предоставляй явный
метод, как `ontology::close()`. Деструктор остаётся безопасным резервным
путём без исключений. Не скрывай ошибку сохранения от явного вызывающего кода.

### Потоковая обработка: пример oww

- Один экземпляр детектора хранит контекст одного аудиопотока; вызовы
  последовательны. Он не является общим потокобезопасным сервисом.
- Контракт входа: 80 мс, 16000 Гц, моно signed PCM16, 1280 отсчётов.
  `PcmFrame` закрепляет размер типом; указатель и вектор требуют полного
  кадра от вызывающего кода, проверка длины намеренно отсутствует.
- Модели загружаются и прогреваются в конструкторе. Рабочие буферы
  и тензоры переиспользуются; не переноси загрузку и подготовку в цикл кадров.
- ONNX Runtime скрыт, ошибки SDK переводятся в стандартные исключения
  с контекстом. Неконечные результаты не маскируются ограничением диапазона.
- Захват микрофона, ресемплинг и порог срабатывания принадлежат другим
  компонентам. Загрузка моделей выполняется отдельной явной командой.

### Хранилище и синхронизация: пример ontology

- `IOntologyStorage` задаёт операции над записями и связями; значения
  возвращаются собственными копиями, без ссылок на память движка.
- Публичные операции сериализованы transaction mutex, включая составные
  чтения. Изменения нескольких связей выполняются транзакционно;
  пользовательские значения передаются параметрами Cypher.
- Рабочая база находится в приватном RAM-каталоге. Сохранение:
  checkpoint → закрытие движка → копия во временный файл → fsync →
  атомарный rename → fsync каталога → повторное открытие при необходимости.
  Не подменяй этот протокол прямой перезаписью постоянного файла.
- Межпроцессный single-writer обеспечивается отдельным lockfile с flock;
  mutex защищает потоки, но не заменяет эту блокировку.
- Фоновых потоков сохранения нет. Приложение вызывает `dumpToFile(path)`;
  `close()` сохраняет только явно заданный `dump_path`, затем освобождает ресурсы.
  Исходный файл задаётся отдельно через `database_path`.
- Ошибка явного сохранения передаётся вызывающему. При неудаче финального
  сохранения `close()` допускает повтор; деструктор сохраняет рабочие файлы
  для восстановления и сообщает об ошибке без исключений.

### Фабрики, реестры и диспетчеризация

Фабрики драйверов инкапсулируют создание конкретных устройств;
`DriverFactoryRegistry` выбирает фабрику по идентификатору, `DeviceRegistry`
хранит созданные драйверы. `DeviceManager` координирует эти компоненты.
`CommandDispatcher` использует таблицу обработчиков и дескрипторы для
валидации команды. Сохраняй это разделение вместо переноса создания
драйверов и доступа к хранилищу в обработчики команд.

### Ошибки и диагностика

Используй существующие типы ошибок и контракты методов. Обычные категории:
`invalid_argument` — некорректные параметры, `logic_error` — нарушение
состояния, `runtime_error` — сбой выполнения или внешнего ресурса;
доменные исключения сохраняй, например `UnsupportedDriverError`.
Не определяй важность сообщения только по классу исключения.

Логируй ошибку на границе её обработки, без повторного логирования
при каждом пробросе. Рабочие потоки не должны выпускать необработанные
исключения: явно выбери повтор операции, сохранение ошибки для вызывающего
или переход в отказавшее состояние. Глобальное управление logging
принадлежит приложению; библиотечные конструкторы не настраивают логгер.
Диагностика идёт через `logging::log`, секреты и полезная нагрузка
по умолчанию не журналируются.

## Архитектура проверок

Ориентиры — тесты OWW с маленькими ONNX-графами и независимым численным
эталоном, тесты ontology с изолированными каталогами и внедрением отказов
на этапах снимка. Приватные test seams находятся в `src/Testing.h`,
не в публичном API. Для конкурентных тестов предпочитай управляемые
события и condition_variable произвольным задержкам.

Основные тесты должны быть воспроизводимыми без внешней сети.
Проверку настоящих моделей, оборудования и производительности на Raspberry
Pi отмечай отдельно: smoke-тест инференса не доказывает качество распознавания,
а тест на рабочей машине не доказывает соблюдение лимитов платы.
При изменении модуля подключай его к CTest и списку входов `cmake/Docs.cmake`.

## Перед изменением
- Прочитай спецификацию затрагиваемой функции.
- Изучи существующую реализацию и относящиеся к ней тесты.
- При конфликте кода и спецификации явно укажи расхождение.

## Требования
- Изменение ожидаемого поведения отражается в спецификации.
- Не ослабляй требования только ради прохождения тестов.
- Существенные допущения явно фиксируй.

## Реализация
- Используй существующие механизмы ошибок и интерфейсы.
- Не включай посторонние рефакторинги в текущую задачу.

## Проверка
- Выполни необходимые проверки.
- В итоговом отчёте перечисли выполненные команды и результаты.
- Невыполненные проверки укажи отдельно.
